devc runs AI coding agents in rootless Podman containers, one **box** per project, with the agents' permission prompts switched off. The idea is to assume the worst of whatever runs in a box: it may run anything, and everything in the box, devc's own helpers included, is under its control. So every decision about a box is made outside it, on the **host**, from a configuration directory no box can write, and whatever a box sends out is treated as hostile input. A box gets only what its project grants: its mounts, a network level, secrets, and access the host brokers to git, SSH hosts, GitHub and web services. Its commits are banked into a relay on the host that records every tip a branch ever had. A **daemon** on each machine keeps a channel to every running box, records every session and types into sessions when asked; a **hub**, if you run one, mirrors the sessions of all machines, notifies your phone, serves a web app and keeps the state machines archive to it.

## How to read the explorer

- **Colours are trust zones**: your devices (brown) and the hub (pink), the host (green), the auxiliary containers the host starts (purple), the box (orange, untrusted), outside services (grey). The [Runtime map](#/runtime) shows what runs in which zone and every channel between them; a diamond on a channel marks a trust boundary, where what arrives is checked. A coloured strip on a name says in which zones that code may run.
- **Every chip and link is a reference** to code or to another page: hovering shows a card, a click opens it in the inspector beside the page, Ctrl or Cmd and a click opens it in full.
- **What the tool checked.** Every reference resolves to code that exists; consecutive steps of a flow are connected in the call graph, or say why the tool cannot see the connection ("not verified by the tool": a goroutine, a queue, a file, another process, a network connection); packages import only from their own layer or below; every file belongs to a concern. **What it could not check** is the prose: the explanations were written from the code and checked against it by a second reader, but no tool proves a sentence true. Where code may run is an over-approximation of the call graph, and tours are reading orders, not checked paths.

## Where to start

1. The tour [[flow:start-here]] follows one task from a configured project to a box that goes down again, in some thirty stops, each pointing to the flow that tells it in full.
2. [[concern:security-model]] states what devc defends against, the six rules every part of the code follows and where each is enforced, what each zone is trusted with, and where the code falls short today. Its tour [[flow:trust-boundaries]] visits every place where something crosses from a less trusted side to a more trusted one.
3. Then the concerns, in the order below, each needing only what came before it: the configuration and the host's foundations, a box and what runs in it, the daemon and sessions, git, the network and brokered access, data, the hub and the archive, and last, how the code is tested.
