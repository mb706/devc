# Independent feature suggestions for devc

**These suggestions are not yet endorsed by the developer. They are only suggestions for discussion, not approved requirements, commitments, or an implementation roadmap.**

Prepared independently without consulting `SUGGESTIONS.md`. The baseline is the current implementation, the [user guide](devc/docs/guide.md), [specification](devc/specs-v2.md), [implementation plan](devc/docs/dev/plan.md), and [recorded deferred work](devc/docs/dev/LEFTOVER.md). Each item proposes additional behavior beyond the existing facilities or their documented plans. Everyday conveniences come first, followed by less obvious gaps and larger possibilities.

1. **Tasks that outlive sessions.** Give a piece of work its own identity, brief, acceptance criteria, and links to its worktrees, sessions, requests, and eventual result. A task could survive several harness restarts or a machine change. This would make “where did that investigation end up?” answerable without reconstructing a sequence of terminal sessions.

2. **Handoffs between harnesses.** Generate an editable handoff containing the goal, decisions, rejected approaches, current revision, outstanding questions, and verification results, with links to the original evidence. Starting another harness could use that packet immediately. This would preserve useful context when changing agents without assuming their native conversation formats are interchangeable.

3. **A deliberate move-to-another-machine workflow.** Coordinate stopping the source session, banking its work, checking required data and environment availability, transferring state, and resuming on the destination. Report anything that cannot travel and record which machine now owns the task. Existing fleet archives provide building blocks; an explicit handoff would make laptop-to-server moves much less manual and reduce accidental duplicate work.

4. **Completion backed by verification.** Let a project define checks in trusted configuration and run them against an exact banked revision in a fresh, restricted box. Attach commands, exit statuses, logs, and environment identity to the result; invalidate the result when the revision changes. Separate “the agent finished its turn” from “the configured checks passed” and “I accepted the work.”

5. **Review comments attached to exact changes.** Extend the Changes view with persistent comments on a file, hunk, or line of a particular banked revision. Send selected comments back to the agent, and track whether a later revision addresses them. This would turn a phone review into a useful revision cycle while keeping each comment's original context available.

6. **Search across past work.** Search journals, archived transcripts, notes, requests, and banked commit messages by phrase, file, error, project, or date, with direct links to the matching evidence. Start with ordinary full-text search and explicit realm filters. Finding “the session where we explained that compiler failure” would make accumulated history useful long after it leaves the live inbox.

7. **Early warnings about overlapping work.** Compare the banked changes of active tasks, including tasks on different machines, and flag overlapping files, migration sequences, or diverging versions of the same branch. Offer a merge rehearsal in a disposable box. These would be advisory signals that help catch duplicated effort and likely conflicts before both tasks are considered finished.

8. **Usage budgets and progress watchdogs.** Show per-task elapsed time, model usage where the harness reports it, and explicitly labelled cost estimates where available. Add configurable alerts for repeated failures, long periods without observable progress, and exceeded budgets, with an optional stop action. Missing telemetry should remain visible; a local stop threshold cannot guarantee a provider's final bill.

9. **Resource limits for the whole workload.** Extend the existing memory and process limits with CPU and disk controls, storage-growth alerts, and admission limits across all boxes on a machine. Include explicit GPU selection where supported. This addresses the case where every individual box is within its allowance but their combined builds, caches, and agents overwhelm the workstation.

10. **Managed development databases and queues.** Define disposable PostgreSQL, Redis, or similar companion services in trusted configuration, with readiness checks, seed data, logs, and resettable volumes. Let tasks have separate instances where needed. The host would manage their lifecycle and restricted connections, giving a project a repeatable application stack without granting the box control of Podman.

11. **Authenticated remote application previews.** Let an enrolled phone open a task's development server through the existing outbound machine-to-hub connection. Give previews expiration, clear task identity, and origins isolated from the hub's control interface. This would make it possible to inspect the actual application while away from the workstation, alongside its transcript and diff.

12. **Attention controls beyond event notifications.** Add per-task snoozing, quiet hours, priority, and a digest of newly finished work, while allowing explicitly urgent events through. Preserve unresolved questions in a durable queue and show when they have become stale. With many sessions, choosing when to interrupt the developer becomes as useful as detecting that an agent needs attention.

13. **A lock record for the complete environment.** Record image digests, harness and toolbox versions, baseline/configuration revisions, and published-share versions together, then check another machine against that record. Existing individual version pins and drift detection could feed this feature. It would explain why the same repository behaves differently on two machines and make known-good environments reusable; model responses would still vary.

14. **Canary upgrades with compatibility results.** Try a new harness or environment version on a disposable project before promoting it across selected boxes. Exercise startup, hooks, status reporting, input delivery, and resume behavior, and retain the previous environment generation. A small compatibility report would reveal when an upgrade silently breaks devc integration even though the vendor executable still starts.

15. **A recovery timeline spanning code, data, and memory.** Present banked revisions, data savepoints, context commits, and environment generations together, with named checkpoints and a preview of what restoration would change. Restore into a fresh worktree or box first. Clearly identify components captured at different times or omitted altogether, so a convenient checkpoint never implies an atomic snapshot that was not actually taken.

16. **Recovery coverage and restore rehearsals.** Answer “what would I lose if this machine vanished now?” with the age and location of recoverable copies, plus uncovered project data, box homes, ignored files, oversized untracked files, configuration, and credentials. Periodically rehearse a restore in an isolated location. This would extend sync status into evidence that the developer can actually get back to work.

17. **Isolated task experiments.** Offer an opt-in task box with its own writable checkout, home, data scratch space, and shared-state policy, seeded from a chosen checkpoint. Two approaches could then run side by side and be compared using their changes and verification results. This is a larger architectural extension: today's worktrees share a project box and data, so separate branches alone cannot isolate experiments.

18. **Draft and published shared memory.** Let agents write candidate memories into a draft area while other tasks consume a reviewed, versioned snapshot. Show the diff when promoting a lesson, and retain links to its originating session and revision. Existing context history helps recover old text; controlled publication would also reduce the spread of stale assumptions or one agent's mistaken conclusions.

19. **An access explainer and configuration impact preview.** For a proposed connection or action, show the effective rule, its configuration source, relevant temporary grants, and the difference between configured and currently running policy. Before applying an edit, explain which boxes need recreation and which capabilities would change. This would extend `config show` and drift detection into practical answers to “why is this denied?”

20. **Task-scoped grants and an emergency quarantine action.** Extend timed network exceptions to suitable brokered service and SSH capabilities, with grants ending when the task ends. Add one action that stops a project's sessions, revokes its broker access, and suspends automatic forwarding while retaining its banked work. Report separately any exposed credentials that still need revocation at their provider.

21. **Transcript disclosure controls.** Allow sensitive sessions to keep raw transcripts local and produce filtered hub views, notification bodies, and archives. Redact known secrets before remote persistence and show what will be exported, covering credentials embedded in ordinary text as well as credential files. This is especially useful with append-only history, where accidental disclosure can otherwise be preserved for a long time; arbitrary secret detection would remain imperfect.

22. **Publish sealed results as fresh copies.** Offer a stronger publication mode that copies or reflinks an output into a fresh vault-owned tree and publishes it only after completion. Existing sealing changes ownership and permissions, but its documented limits include previously opened writable file descriptors. Fresh inodes would prevent those old handles from modifying the published copy; consistent capture would still require coordinating active writers.

23. **One managed tool catalog across harnesses.** Define external tools, including MCP servers, once in trusted configuration and generate the corresponding setup for each supported harness. Manage server startup, health, declared permissions, and visible tool-schema changes, with executable servers running in restricted containers. Switching harnesses could then preserve the available tools as well as the working files.

24. **A network fault laboratory.** Add an opt-in testing mode for task traffic with reproducible latency, connection failures, bandwidth limits, and outages, while retaining existing access restrictions. Tie the selected scenario to verification results. It would make “does the app recover when its API disappears halfway through?” a repeatable local experiment instead of something discovered only after deployment.
