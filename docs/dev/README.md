# Development guide for devc v2

Read this before working on any chunk.

## Documents

| File | Role |
|---|---|
| `specs-v2.md` | Product spec: what devc does and why. |
| `docs/dev/plan.md` | Implementation plan: package map, cross-cutting technical decisions, chunk list. |
| `docs/dev/chunks/Cnn-*.md` | Work orders, one per chunk. Authoritative for scope and detail. |
| `docs/dev/STATUS.md` | Progress log. Update it at the end of every chunk. |
| `docs/dev/LEFTOVER.md` | Checks that could not be run and work that was deferred. Append to it. |
| `docs/dev/reviews/` | Review reports and responses. |

If a work order conflicts with the plan or the spec, follow the work order and record the conflict in `STATUS.md`.

## Security rules for code

These implement rules R1–R6 of the spec. A violation is a bug even if everything works.

1. **Policy comes only from the config directory.** Never read settings from a project directory, a box home, or anything else a box can write.
2. **Box-writable data is hostile input.** That covers the project directory, box homes, the runtime directory and spool, and harness state.
   - Host code never executes anything from there and never runs git, an interpreter or a build tool with such a directory as working directory.
   - Host code does not walk project trees. Operations on them run inside the box (`podman exec`) or in the helper container. One exception: `restorecon -R` on SELinux hosts, a system tool that does not follow symlinks and only changes labels.
   - Where the host must read a single file from such a place (spool files, for example), open it through `internal/safefs`: resolved beneath a directory file descriptor with no symlinks, regular files only, with a size cap. Parse strictly and validate every field.
   - Never join a box-supplied name into a host path without validating it first.
3. **No shell interpolation.** Start subprocesses with argument vectors. Do not build `sh -c` strings from values on the host. Inside boxes prefer argument vectors too.
4. **Names are validated.** Realm, project, env, worktree, harness and session names must match `^[a-z0-9][a-z0-9._-]{0,62}$` before they appear in a path, a container name, a ref or a label. Session IDs are generated by devc and validated when read back.
5. **Secrets stay out of argv, environment dumps and logs.** Pass them over stdin or in 0600 files. Redact them in errors.
6. **Fail closed.** If a protection cannot be applied (firewall rules, seccomp profile, a read-only mount), the operation fails with a clear message. It never continues without the protection unless the user passed an explicit flag.

## Engineering conventions

- **Language and build.** Go, module `github.com/mb706/devc`, `CGO_ENABLED=0`, one static binary. The toolchain runs in a container through the `./dev` script; there is no Go on the host.
- **Machine-agnostic code.** Tests run on this host (Ubuntu 24.04, rootless Podman 5.8.3 with slirp4netns, fuse-overlayfs and runc, AppArmor user-namespace restriction, no SELinux, no KVM, host UID 1001). Code must not assume any of that. Detect, do not assume; SELinux paths must be implemented even though they cannot be tested here, and noted in `LEFTOVER.md`.
- **Dependencies.** Standard library first. Approved: `spf13/cobra`, `BurntSushi/toml`, `golang.org/x/sys`, `golang.org/x/term`, `creack/pty`, `hashicorp/yamux`, `coder/websocket`, `modernc.org/sqlite`, `go-webauthn/webauthn`. Anything else needs a line in `STATUS.md` saying why.
- **Errors.** Wrap with `%w`. User-facing messages are lower-case, say what failed and what to do. Exit codes: 0 success, 1 failure, 2 usage error.
- **Logging.** `log/slog` to stderr; `-v` raises the level. Normal output goes to stdout and is stable enough to script against; offer `--json` on listing commands.
- **Context.** Every external command takes a `context.Context` and has a timeout.
- **External commands** (`podman`, `git`, `nft`, `nsenter`, `ssh`) go through small wrapper packages so tests can substitute fakes.
- **Formatting.** `gofmt` and `go vet` clean.
- **Comments** say why, not what. Each package has a doc comment stating its responsibility and which security rules it carries.

## Tests

- **Unit tests** sit beside the code and use only the standard `testing` package. Use fakes for external commands.
- **Integration tests** live in `test/integration` behind the build tag `integration` and run on the host against real rootless Podman (`./dev itest`).
  - They use temporary config and state directories (`DEVC_CONFIG_DIR`, `DEVC_STATE_DIR`, `DEVC_RUNTIME_DIR`). They never touch `~/.config/devc` or `~/.local/share/devc`.
  - Containers are named `devc-it-…` and labelled `devc.test=1`. Every test cleans up after itself, also on failure.
  - No test needs a real harness login. Agent behaviour is exercised with the fake harness introduced in chunk C03.
- **Economy.** While working, run the tests for the packages you touch. Run the whole suite once, at the end of the chunk.

## Rules for the shell

- **Never use `rm` with an unguarded variable.** Commands such as `rm -rf "$DIR"/*` are blocked by the environment until a human intervenes, which stalls the work. Write `rm -rf "${DIR:?}"/*`, or use a literal path. This applies to commands you run and to scripts you write.
- Do not remove or prune Podman objects you did not create. Clean up the containers, networks and volumes you do create.
- No `sudo`. No real harness logins. No `git commit` and no `git push`: the orchestrator commits after reading your report.
- Network access is for pulling images, Go modules and pinned release downloads only.
- Use a directory from `mktemp -d` for scratch files, not the repository.
- Do not start sub-agents. Do the work yourself, sequentially.

## End of a chunk

1. Run the full unit suite and the integration tests the chunk touches.
2. Update `docs/dev/STATUS.md`: what now exists, deviations from the work order and why, how to exercise it.
3. Append to `docs/dev/LEFTOVER.md` anything that could not be verified here or was deliberately deferred.
4. Reply with at most 300 words: what was built, deviations, tests run with results, open problems. Do not paste code or long logs.
