# Response to the verification of the last fixes, part 1

All fifteen findings of `E1-review.md` and the unconfirmed E1-16 are resolved in chunk C19r3 as the work order directs; E1-16 was measured and confirmed. Tests named below are unit tests unless marked otherwise; each refusal test has a positive control in the same test.

**E1-01 — fixed.** `Uploader.snapshot(f, src, max)` checks the size cap after every stat (the first and each retry's) and copies through `io.LimitReader(…, max)`, so no copy writes more than the cap; a file beyond it is counted as skipped. `fleet.TestSnapshotLimits` turns a small mutable file into an 8 GiB sparse file during the first copy: refused, no snapshot left, nothing archived; a direct call with a stale small stat is refused too; a file within the cap is copied whole.

**E1-02 — fixed.** Before anything is created (`archiveStore.planNew`), every name the hub will write for a new file (data, `~meta`, `~meta.tmp`, a bundle's `.part` and final name) is checked against the hub file system's own name limit (`statfs` `f_namelen`; fuse-overlayfs allows 251) and against 4096 bytes. The file, its missing directories and a new realm are checked against the quota and `max_realms` (directories now count against `max_files`), and only then created (`create`), counted one by one. A failed upload removes its files and directories and gives back what was counted; a failed append is cut back to its old length. `archive.ValidRel` limits file names to 238 bytes so the suffixes fit in 255, and the box-side worker skips longer names. The same path serves ref logs, bundles and secrets bundles. `hub.TestArchiveNamesAndDirectories`: names one byte too long (by the archive's rule and by the file system's), a hub-side check bypassing the parser, a third realm over `max_realms`, and fifty uploads under fresh realms whose data cannot be synced: nothing is left and the kept usage equals a fresh count. The same uploads pass without the failure.

**E1-03 — fixed.** The listing cache (`genCache`) holds at most 64 directories and 100,000 generations per machine (least recently used go first). Entries are added only for existing directories, after an upload into them succeeded, and the quota check comes before any listing. `hub.TestArchiveListingCache`: 300 uploads naming fresh directories over the quota cache nothing; a refused older generation caches nothing while a successful upload does; 104 directories stay within the bounds; an evicted directory still refuses an older generation.

**E1-04 — fixed (retention redesigned).** The hub decides the classes: `class=mutable` outside `files/harness/` gets 400 (`archive.MutableAllowed`), and a file keeps the class of its first generation (409 with `class` in the answer). The uploader follows the hub's class, from the index for new bookkeeping or from the 409 (`FileState.Fixed`, `adoptClass`). The first completion records the hub's time (`completionTime`: never before an older generation's), and completing a generation after a newer one is refused. Retention (`retention.go`, pure `retentionDrops`) keeps the newest three complete generations and the state at every checkpoint, the starts of the last `keep_daily` (7) days and `keep_weekly` (4) weeks, UTC, weeks from Monday. It drops nothing while the clock is behind the file's records. It drops only generations recorded as mutable, beneath the file's directory (`unlinkat` on a directory descriptor), after the completion record is durable. `hub.toml [archive] keep_daily/keep_weekly` are validated and documented. `devc state pull --as-of` restores the newest generation completed by then (`Entry.Completed` in the index), leaves out later files and reports what it took as it is now. Tests: `hub.TestCheckpoints`, `TestRetentionDrops` (months unchanged then forty rewrites in a day, fifty in one day, a clock stepping back, generations without times, append-only), `TestRetentionHostile` (40 random hostile histories over months with clock steps: after every run the state at every checkpoint is there and at most 14 complete generations remain), `TestArchiveClasses` (the review's scenario, ten generations in a minute two days later, the clock stepping back, sealed generations, out-of-order completion, no time from the machine), `TestArchiveRetentionConfig`; `fleet.TestClassAdoption`, `TestRestoreAsOf`.

**E1-05 — fixed.** `writeMeta` returns write, sync, rename and directory-sync errors and returns nil only once the record is durable. `appendFile` syncs the directory when it creates a file, and a bundle's rename is followed by a directory sync. Retention runs only after a durable first completion; a completion answered again syncs the directory before it says "complete". `hub.TestArchiveDurableCompletion` makes the record's sync and then the directory's sync fail (500, nothing dropped, the record does not take effect), checks that the directory sync of the next completion happens while the old generation still exists, and that it is dropped after (the positive control).

**E1-06 — fixed.** `chooseGenerations` decides per generation. A completion record makes a candidate at its committed length; no record at all makes a candidate at its stored length; a record without completion is incomplete and never used while an older candidate exists. Nothing is guessed for the whole archive (`legacyArchive` is gone). `fleet.TestRestoreMixedFormats` restores the old database without a record behind a partial replacement, with and without an unrelated committed file; with no candidate, a mutable file is left out and an append-only one is restored as far as it goes.

**E1-07 — fixed.** `snapshot` returns the accepted copy's length and the stat taken with it; the generation's `SnapSize`, `Src`, mode, upload and completion use only those values. `fleet.TestSnapshotLimits`: a file that grows during the first copy is archived whole and completed at its new length; one that shrinks completes at five bytes instead of waiting for a tail that does not exist.

**E1-08 — fixed.** A completion conflict is reconciled like an upload conflict (`commit` → `fileConflict`). The upload moves to a new generation when the stored one is longer than the source or complete at another length, and resumes otherwise; `send` then goes on uploading and completing, at most four rounds. A 409 without a length (an older generation, or a newer complete one) makes the next pass read the index again without failing the pass; a 400 skips the file. `fleet.TestEmptyReplacement`: an append-only log and a mutable file truncated to empty after the bookkeeping was lost become empty complete generations in one pass; a second pass adds nothing, and lost bookkeeping over unchanged files adds nothing.

**E1-09 — fixed.** Admission counters have their own lock (`admMu`), held only to count. The global and the machine's place are reserved together or not at all, a refusal is immediate, and the release takes the same lock. Summaries read usage under its own lock (`umu`), and a prune resets bookkeeping per machine through an epoch instead of locking every machine. `hub.TestArchiveAdmissionNoWait` holds one machine's write lock: four of its six uploads get 429 at once, two wait on their own places, and the other machine's upload, summaries, index and download answer at once. No place is left taken afterwards.

**E1-10 — fixed.** The stall deadline belongs to the admission wrapper (`Server.admitted`): every admitted response gets a write deadline before its first byte and on every write, or is refused if one cannot be set, whatever the endpoint (upload, file, hash, index, summary, secrets). `hub.TestArchiveStalledResponses`: a client that stops reading an index page, the summary, a secrets bundle or a file loses it and frees the only read place within the stall limit (small socket buffers on loopback); read normally, each is served whole.

**E1-11 — fixed.** `api.command` keeps uncertainty across attempts. Once an attempt's outcome is unknown, a later definite refusal is raised as uncertain too, so `run` keeps the command pending with its ID and parameters. `retryPending` passes `unsure` unless the machine said it never received the ID (`unsent`), so a refused retry of an uncertain command stays pending. `web/check.sh` logic checks: a broken answer followed by a 503 leaves the command pending under its ID after two attempts; a refused retry keeps it pending; a refused retry of an `unsent` one fails. With the old modules the check fails.

**E1-12 — fixed.** `Proxy.watch` registers the connection, checks the policy again synchronously and starts the watch from that state. Both `connect` and `plain` (new and reused upstream connections) call it after the connection exists and before the tunnel is acknowledged, a `100 Continue` is sent or a byte is forwarded; a refusal is answered 403 and logged. A recheck asked for during that check is not lost. `netpolicy.TestProxyTunnelStart`: an exception that expires during resolution and one revoked during dialling, each for CONNECT with an early request and for a plain request: 403 and the upstream receives nothing; still allowed, the early bytes arrive. It fails on the old proxy.

**E1-13 — fixed.** Paging back detaches the window (`timeline.detach`): live events only raise `newest` and settle the outbox, so the window does not move while a page is read. An older page is applied when the window's first event is unchanged and no full reload started since. The screen shows how many newer events are not shown, next to **Back to the latest**. `web/check.sh`: a window of 1,000 events gets its older page although 50 live events arrived meanwhile (1,000 held, 250 newer counted); the action run pages a 2,600-event session back to its start and returns.

**E1-14 — fixed.** In `applyChange`, an event first goes to the loading buffer whenever a full read runs, and only then is the window checked for being detached. **Back to the latest** goes through the same loading state as opening a session, and `replace` merges buffered events by seq. `web/check.sh`: an event that arrives while the latest events are read is in the window afterwards, which is live again.

**E1-15 — fixed.** `headBudget` sets the limit of each head to 64 KiB minus what the buffer already holds, so a head consumes at most 64 KiB counting carried-over bytes, for upstream response heads and for the client's pipelined request heads alike. Interim answers stay bounded at eight. `netpolicy.TestProxyHeadBudget`: a 72 KiB final head right after a `100` is refused (502) and a 60 KiB one passes; a pipelined second request with a 72 KiB head is refused (431) and one with 60 KiB is forwarded. It fails on the old proxy.

**E1-16 — confirmed and fixed.** Measured with git 2.43 on this host (a 200 MB incompressible push, `receive.unpackLimit=1`, receive-pack in its own session as devc runs it). SIGTERM to receive-pack alone ended it in 25 ms, but index-pack went on. While receiving, it grew the quarantine from 24 to 134 MB; while completing a thin pack, from 16 KB to 205 MB (it appends the delta base). After the quarantine was removed it was still running, writing into a deleted file. Signalling the process group ended everything in 45 ms, with the quarantine unchanged; fsck passed in both cases. New `execx.Cmd.KillGroup` gives the command its own process group (or uses its session), sends the cancellation SIGTERM to the group, kills the rest of the group as soon as the leader exits but before it is reaped (so the group number cannot be reused meanwhile), and waits until no process of the group runs (zombies not counted). `gitx.Host.Serve` and every git command of a background (daemon) host use it. `Daemon.runPush` removes quarantines only after the group is gone and leaves them with an error log if the group did not end. `execx.TestKillGroup` (cancelled, in its own session, leaving children behind, and without the option as the control); `daemon.TestPushEndedDuringIndexPack` with real git: the watchdog ends a 96 MB push while it is received and a thin push while index-pack completes it. Afterwards no git process works in the relay, there is no quarantine, temporary pack or lock, the relay does not grow and passes fsck, and the next push succeeds. Without the group kill the thin-pack case fails (index-pack still running).

**Neighbouring paths checked.** Ref logs, bundles and secrets bundles share the creation and accounting path with files; bundle completion syncs its directory; summaries and prune resets no longer wait on a machine's writes; the uploader's 409 and 400 handling is the same for uploads and completions; the proxy's request heads use the same budget as response heads; the fetch-through, box fetches, bundle fetches and archive git of the daemon end their process groups too. Git run by command-line commands stays in the terminal's group (an interrupt ends it), recorded in LEFTOVER.
