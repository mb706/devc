# Response to the verification of the last round, part 2 (E2)

Chunk C19r4. Every finding of `E2-review.md` (against `f1b7e15`; C19r3 did not touch these areas) is resolved as the work order's decisions table directs, and the flaky `TestWebApp` step turned out to be a product bug, fixed at the end. For each fix the neighbouring paths were checked; what was found is in the paragraph. Tests named below are new unless marked as extended.

**E2-01 (existing desktops) — fixed.** The sidecar now records what it was created with in two labels: `devc.gui.limits` (`memory=<bytes> pids=<n> cpus=<n>`, `none` for a limit switched off, derived from the very arguments it is created with) and `devc.gui.image` (the generation of the image, read back from the image's `devc.aux.hash` after it is built; a tag rebuilt by another devc meanwhile refuses the start). `gui up` on a running sidecar of the box's current start compares both with what it would create now (`Manager.outdated`): a difference, or a sidecar without the labels (created by an earlier devc, possibly without limits), fails with the difference named and `'devc gui up --restart <ref>'`; nothing is removed, created or forwarded. A running sidecar whose record (password, forward) is gone is refused the same way instead of being replaced silently, the neighbouring case of the same rule. `gui status` reports such a sidecar as `outdated` (or names the missing record). Tests: `gui.TestOutdatedSidecar` (a sidecar without limits or records, as an earlier devc left it: refused, untouched, status outdated, `--restart` replaces it with limits and records; changed `[gui] memory`: refused naming both specs, restoring the setting reuses it; another image generation; a missing record), `TestSidecarArgs` and `TestLimitArgs` (extended: the labels, `LimitsSpec`); integration `TestGUI` (extended: with `memory = "1g"` the running desktop is refused and keeps its container ID, status `outdated`, `--restart` gives a 1 GiB desktop with a new password, and changing back needs `--restart` again).

**E2-02 (padded credentials) — fixed.** A header credential is normalised once, in `svclogin.HeaderCredential(header, stored)`: one trailing line ending, then spaces and tabs around it are removed; control characters, DEL and bytes outside printable ASCII are refused. Its words are split at spaces and tabs; a first word in a short fixed list of schemes (`Basic`, `Bearer`, `Token`, `Bot`, `Key`, `ApiKey`, `Api-Key`, `SSWS`, `OAuth`, any case) is public; every other word, and Basic's password, needs 8 characters; the whole value, every secret word and Basic's decoded user:password and password are scrubbed. It returns the `Credential` itself, so the daemon forwards and scrubs exactly the value that was checked (`ScrubValues`/`CheckCredential` are gone). Before, a first word that was not a scheme was never scrubbed on its own (`secret1x secret2y`); that is closed too. The proxy's last check (`Credential.check`) refuses a value not in normal form, a value missing from the scrub list, and any scrub value under 8 characters. Logins: cookie names and values are trimmed the same way where they are loaded (`ParseLoginOutput`, `ParseJar`), then checked as before; login secrets are also redacted without surrounding white space. Tests: `svclogin.TestHeaderCredential` (replaces `TestScrubValues`: twelve accepted forms with their scrub lists, sixteen refusals whose messages never contain the value), `TestProxyPaddedCredential` (three padded credentials: the upstream gets the trimmed value, reflects it in a header, the box sees only `[devc: redacted]`; `abcdefg ` is refused), `TestProxyShortCredential` (extended: padded and control-character values handed to the proxy directly are refused with nothing sent), `TestParseLoginOutput`/`TestJar` (padded cookies), and end to end in `daemon.TestServiceStreams` (extended: a padded stored token reflected by the upstream; `abcdefg ` answers 503 and reaches nothing).

**E2-03 (CRAN index) — fixed.** `depsrc.ParseDCFAll` parses a control file completely: LF and CRLF, continuation lines, a 1 MiB line bound; a scanner error, a line that is no field, a field name with blanks or empty, a continuation without a field or a repeated field is an error, never a partial result. `cranCurrent` parses the whole `PACKAGES` (bounded by the 64 MiB document limit as before) and also refuses a stanza without `Package` and a package listed twice; any such error fails the download. Only CRAN's archive of old versions may be downloaded without a checksum: a named version that is not the index's current one has the archive URL as its only candidate, so a version in neither is an error (before, `src/contrib/` was tried unchecked first). Neighbours: an installed `DESCRIPTION` is parsed by the same strict parser (`ParseDCF`, one stanza) and one that is larger than 1 MiB or does not parse is an error instead of a partial version; PyPI and npm answers were already strict JSON. Tests: `depsrc.TestParseDCF` (LF/CRLF, six refusals, a broken `DESCRIPTION`), `TestFetchCRANIndex` (a CRLF index with the package second: verified with its MD5, refused with a wrong MD5; an overlong line before and inside the stanza, a line that is no field, the package twice, a stanza without a name: refused with no download; a version only in `src/contrib`, which the stand-in serves there, is not downloaded; archived and current controls).

**E2-04 (skipped entries) — fixed.** The pull-in worker records the merge's outcome for every entry: `merged` (everything the remote had is here), `skipped` (a sealed entry left alone because it differs), `partial` (something below the entry left out: a special file, a file that vanished or could not be read). It travels in the entry itself (`EntryDigest.Remote`, `.Outcome`) and into the pull record (`Record.Outcome`, validated); `data status` marks a remote matching only when its last pull's outcome is `merged` and what arrived equals the entry now, never from equal listings alone. Pull records written before this have no outcome and do not match. An entry that arrived as no data (a special file where this machine has a file) has no observation of the remote and is `partial`; the host accepts a missing observation only for an entry that is not `merged`, so such a pull does not fail after its merge. Tests: `boxside.TestPullInSpecialEntry`, and `data.TestPullRemoteObservation` (extended: a sealed entry with `result = AAAA` here and `result = BBBB` on the remote, and an entry that arrived with a FIFO in it, both with equal listings: recorded as `skipped` and `partial`, not matching; checked to fail with listing-only matching).

**E2-05 (report size) — fixed.** The worker prints its report compactly (`boxside.MarshalReport`: no indentation, no HTML escaping), one entry carries both observations (`remote_digests` is gone), and the capture limit (`RunOptions.MaxOutput`) and the decoding limit are one value, `boxside.MaxReport` (64 MiB); a cut capture is an error. A pull records at most `MaxSyncEntries` (100,000) entries, and only as many as fit the report with their names (`CheckPullEntries`: a fixed per-entry overhead plus each path's JSON size, against `MaxReport` less what the capped lists can take). The host checks that against the dry run before anything is transferred (`previewEntries`, `PrintedPathCost` bounds the JSON size of a name from rsync's listing); the worker checks it again against the staged tree before anything is merged (a continued pull may hold more than its dry run listed). To keep the rest of a report bounded, the worker caps skipped texts at 512 bytes each and lists at most 100 displaced paths (`displaced_total` keeps the count). Neighbours: a push now checks the same limit before staging anything; a pull's trash entry rewrites `meta.json` with every displaced path and cannot be read back above 1 MiB, which is unchanged and in LEFTOVER (deferred work). Tests: `boxside.TestReportBounds` (a 2,000-entry report with escape-heavy names and full lists stays within its bound; rsync's listing never costs less than the JSON; 100,000 entries pass and 100,001 are refused; 40,000 names JSON makes six times longer are refused, the same count of plain names passes), `TestPullInEntryLimit` (with lowered limits: one entry too many, and one byte too few, refused with the data root unchanged; at the limit merged; a push at and above the limit), `data.TestPullEntryLimits` (a preview of 100,001 entries is refused with no transfer, no staging and no records; 100,000 entries are transferred; a report of 100,000 entries decodes within the capture limit and one of 100,001 does not; pull-in digests without an outcome, `merged` without an observation of the remote, or with an invalid one are refused; a `partial` one without an observation decodes).

**E2-06 (moving npm names) — fixed.** `concrete` treats an npm version as fixed only when it is an exact semver version (`1.2.3`, `v1.2.3`, with pre-release or build parts); a dist-tag such as `latest` or a range is resolved with the registry every time and never stored as an alias, and an alias an older devc stored for a tag is ignored. Other ecosystems: PyPI and CRAN have no tags or ranges (a named version is one release); a GitHub branch or tag is never cached under its name (its commit is asked for every time and the tree cached under the commit), which the guide now says. Test: `depsrc.TestFetchMovingNames` (`npm:plain@latest` follows the tag from 1.0.0 to 1.1.0, always asking the registry; exact versions come from the cache without requests; a stale `.alias-next` is not used offline; the exact-version rule on thirteen strings), `TestFetchCachedOffline` (extended: `npm:plain@latest` fails without the registry).

**E2-07 (empty cookie header) — fixed.** `svclogin.Jar.Credential(host, path, now)` builds the cookie credential in one place: when no stored cookie applies to the path the header is empty, nothing is added to the scrub list but the stored values, and the request goes out without a `Cookie` header (the box's own is still removed). The minimum still applies to every stored value. The daemon uses it instead of assembling the credential itself. Tests: `svclogin.TestJar` (extended), `TestProxyCookieLogin` (extended: `/health` with a cookie for `/private` is forwarded without `Cookie`, `/private/x` with it), end to end in `daemon.TestServiceStreams` (extended, same two requests).

**E2-08 (lock names) — fixed.** `paths.SyncLockFile` is `local/locks/sync/<realm>/<project>/<remote>.lock`, one validated component each (the sync lock already created its directory with `Ensure`). Realm names cannot contain `-`, so box names were not ambiguous; project and remote names can, and those collided. Other lock files use a single validated name. Tests: `paths.TestSyncLockNames` (nine combinations that joined with hyphens or dots would collide get distinct files; an invalid remote panics), `TestLayout` (extended).

**E2-09 (overflow test) — fixed.** `TestSyncPreviewAndLock` gives each refusal its own capture limit: the cut preview 64 bytes, the unparseable and the overflowing ones 1 MiB, which their fixtures are checked to fit; each case asserts the message only its refusal gives ("longer than", "is not one rsync prints", "add up to more than") and that its dry run ran with that limit. Checked: with `Totals`' error ignored in `Pull`, the overflow case fails.

**The flaky `TestWebApp` step — found and fixed (a product bug).** Eight separate runs of `TestWebApp` with the code before this chunk (four with all twelve cores busy), temporary tests that repeated the control-terminal step 40 times and steps 4 and 5 three times, and 90 inputs written 0 to 1 s after `podman exec -it` of the same tmux client did not reproduce it; the full integration run of this chunk did, and the daemon's log showed the cause one step earlier: the prompt step 4 sends while the terminal observes ended `unknown` with "sending keys: tmux: client is read-only". The observing client was tmux's read-only client, and tmux refuses `send-keys` from any command line while such a client is the best client of the most recently active session (reproduced every time against the static tmux 3.8; `paste-buffer` still works). So the daemon pasted the prompt but its submit key was refused: the text stayed in the agent's input line, step 4's check of the screen was satisfied by its echo, and the text typed in step 5 was appended to it, so its prompt never came. It depended on whether the observer's client had attached (about 0.3 s after `terminal.open`) before the daemon typed. Outside tests: any prompt sent while someone watched the session in the web app was typed but not submitted. Fix: `tmux.Observe` no longer sets `read-only` (only `ignore-size`); observing stays enforced by the daemon, the only writer of the client's terminal, which refuses `terminal.input` for an observing stream, and by the hub. Tests: `tmux.TestObserve` (no read-only flag in either mode); `TestWebApp` step 4 now waits until the observer has drawn the pane before sending and requires the send to be `delivered` and its prompt event to arrive. Against the old flags that step fails every time (checked, with the same "client is read-only"); with the fix `TestWebApp` passed five times in a row (see `STATUS.md`).
