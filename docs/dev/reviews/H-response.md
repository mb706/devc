# Check H of the C20 fixes: outcome per item

The ten findings of `H1-review.md` (C20a), `H2-review.md` (C20b) and `H3-review.md` (C20c), and the failing `TestSmoke`, resolved in chunk C20d as its work order's table decides. Each fix has a regression test that fails without it (checked by putting the old code back, or the old rule, and running the test); each refusal test has a positive control.

## H2: C20b

**H2-01 (high), settlement could delete the record of an accepted tag: fixed as decided.** Crash analysis first: every operation that moves relay refs holds the box lock (receive-pack with its hooks, a bank, a pull, a fetch-through, `devc push`, `project init`, an adoption, forwarding inside post-receive or a bank); a restore only creates missing refs. After a crash between receive-pack and settling, a fetch moves tags with `--force` and a pull fast-forwards branches, so no later look at a ref proves that git refused an update. Now only `gitx.Service.SettlePush`, which the daemon runs right after receive-pack with the box lock held since before it started, removes a record, and only one named in that push's records note (written by its own update hooks, each record created new) whose update git did not apply. Every other settling is `gitx.Service.SettlePending`: it confirms every pending record and removes none. Every operation that moves refs runs it first through `gitx.Service.settleFirst` (`Bank`, `Pull`, `FetchThrough`, `Push`, `InitRelay`, `Adopt`; the daemon before receive-pack). In the ordinary case a refused `main/<t>` record still goes (the X7 3 defect stays closed). Test: `cli.TestRelayHooksSettle` (rewritten; real receive-pack with devc's hooks): the push of `v1` is accepted and nothing settles, the upstream has `v1` elsewhere, `gitx.Service.Pull` settles first and then moves the tag, the record of the accepted `v1` stays confirmed and archived, and so after the settling a bank runs; the same with the tag moved by a raw fetch before any settling, followed by another push whose own settling removes nothing of the earlier push; records left by a crashed daemon, a refused one included, are confirmed; control: the refused `main/<t>` removed when settled right after its push. `gitx.TestPendingRecords` (a bank confirms, removes none).

**H2-02, box-tip observations lost when the daemon died before settling: fixed as decided.** `pre-receive` notes the box's own branches the push updates (`cli.pushedHeads`); the update hook reads the note and gives a branch record whose tip is the box's own an own marker, `refs/devc/pending/own/<kind>/<name>/<time>` (`gitx.pendingMarker`; `SortRefs` reports `PendingOwn`). Whichever settling confirms such a record moves the box tip in the same transaction when the branch still has that tip (falling back to confirming without it). Since every ref-moving operation settles first, the branch still has the pushed tip then. Test: `gitx.TestPendingAfterCrash`: box tip F1, the box pushes B and tag `t1`, nothing settles, the upstream moves `feature` to C (a descendant of B) and `t1` elsewhere; the pull settles first (box tip B, `t1`'s record of B kept and archived), then advances `feature` to C, and the next bank keeps C; control: a push to a branch the box does not have as its own moves no box tip. `gitx.TestRecordPush` passes.

**H2-03, a forwarding bank ran before the pull-request checks: fixed as decided.** `cli.checkPRBranch` (base, project default, the relay's HEAD, `git.protected`) runs first, before the bank; the bank and its forwarding of `git.forward` branches follow; then `cli.checkPRBanked` requires the branch in the relay; only then is anything pushed. Refusals say "nothing was banked or pushed", or "nothing was pushed for the pull request". Help text, guide and the explorer's invariant say so. Test: `cli.TestPRCreateChecksFirst` (extended): with a running box and `git.forward` listing `develop` and `main`, the base, the default branch and a protected branch are refused with no exec in the box (nothing banked or forwarded); control: `feat/x` is banked first.

**H2-04, a daemon goroutine that did not recover: fixed as decided.** New `daemon.afterFunc` and `daemon.contextAfter` run timer and context callbacks under `recoverTask`; the turn banker's timer and the two `context.AfterFunc` aborts (`rawStream.guard`, the host dial) use them. Test: `daemon.TestNoBareGoroutines` now parses the package for `go` statements outside `goTask`/`goSafe` and for `time.AfterFunc`/`context.AfterFunc` outside the two helpers; each failure says what to use instead. Control: a source made for the test with each kind is found. With the old `turns.go` it fails, naming `afterFunc`.

## H1: C20a

**H1-01, a pruned journal came back at the next ingestion: fixed as decided.** `session.Store.Prune` claims an unclaimed ID, writes the mark `<journal dir>/<id>.pruned` (synced) before it removes the journal, keeps the owner record and removes the spool file beneath the box's runtime directory (`safefs`). `ingestFile` removes or skips the spool file of a marked session for good; `AppendHost` refuses to start a marked session's journal again. Test: `session.TestPruneSpoolTail`: a session its budget stopped ends and is pruned; its spool file is gone, its ID stays claimed; the box writes the file again and the budget is raised, yet no journal comes back and the file is removed again; a host event is refused; another project cannot claim the ID; control: another session's events are ingested. `TestJournalProjectBudget` now expects the owner records kept.

**H1-02, a box could hold every slot of a forward after its clients went: fixed as decided.** `netpolicy.Forwarder.relay` watches the socket it hands to the dial process, without reading it, every 250 ms (`clientGone`: `POLLRDHUP`, `POLLHUP` or `POLLERR`); once the client's side has ended, the dial process gets `Forwarder.Grace` (default `ClientGoneGrace`, 10 s) and is then killed, which frees its place. Test: `boxside.TestForwardClientGone` with the real dial helper (the test binary started as nsenter runs `boxside.Dial`) and a box listener that never closes or answers: two clients that went away would hold both places of a forward with two; after the grace a third is served; control: that client stays connected past three graces and gets the box's answer.

**H1-03, the explorer promised a free-space reserve for savepoints: page corrected as decided.** The `security-model` invariant now says what the code does: pushes and banks start only with 1 GiB free and are ended below 512 MiB, journals keep 1 GiB, requested savepoints are bounded by count (`requested_keep`) with no reserve of their own. No other page claimed it.

## H3: C20c

**H3-01, terminal confirmation broke a hub or machine that was not upgraded: fixed as decided.** The hub announces `terminal.confirm` in its answer to `hub.hello` (`proto.HubHelloReply.Features`, `proto.FeatureTerminalConfirm`); machines decode that answer leniently, so an older machine ignores it. The machine requires confirmation from every opener except a hub link whose hub did not announce it (`daemon.hubManager.unconfirmed`, asked at the 30 s deadline). The hub confirms every terminal; a machine older than the method answers "unknown method", which the hub takes as a terminal that needs none. Decided within the table: machines do not announce, since a hub decodes the hello strictly and an older hub would refuse a new field. The entry in `LEFTOVER.md` part 4 is removed. Tests: `daemon.TestTerminalConfirmByHello` (two fake hubs, neither confirms: the announcing hub's stream is ended, the other's kept), `hub.TestTerminalOlderMachine` (the hello's answer announces the feature; a machine without `terminal.confirm` gets an open terminal); controls: `daemon.TestTerminalConfirm`, `hub.TestTerminalOpenCleanup`.

**H3-02, a re-read need not reach the position it advertised: fixed as decided.** `hub.checkTail` requires the events to be consecutive and the last to be the view's `LastSeq` exactly (no events only for a view at 0); anything else closes the link and the hub keeps what it held. So that an honest daemon passes, `sessions.get` answers no events for a view at 0 (before, it read up to event 1). Test: `hub.TestResyncSuccession` with three new cases: events 1 to 3 for a view at 7 (the review's scenario), a view at 5 with events to 7, no events for a view at 7; control: the untouched re-read applied.

**H3-03, a notification that may have been published was forgotten: fixed as decided.** The attempt is recorded durably before it goes out (`Tries+1` stored first, as since C20c), and `hub.attempted` reads it from the record: pending with tries, sent with its sequence ID, cleared. A record handled without a message because a client follows the session keeps its sequence ID when a publish was attempted. Every record whose state ended goes through `hub.notifier.retire`, which drops it only when no publish was attempted and clears its message otherwise (`clear` drops it once ntfy confirms, or after seven days). Test: `hub.TestNotifierWatchedAfterAttempt`: ntfy takes the message but the answer is lost, the user opens the session, the retry marks it handled with its sequence ID, the state's end clears that message; control: a state that arrives while the session is watched is never published and goes without a clear. Also `TestNotifierRetries` now waits for the stored outcome instead of reading it the moment the fake ntfy has the message (a race seen once in this chunk).
