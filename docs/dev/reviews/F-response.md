# Response to the closing check (F1, F2)

Chunk C19r5. The four confirmed findings of `F1-review.md` (against `53b187d`) and `F2-review.md` (against `c336d39`) and the unconfirmed F1-U1 are resolved as the work order's table directs. Tests named below are new unless marked as extended.

**F1-01 and F1-U1 (process groups) — both treated as real, fixed together in `internal/execx`.** With `KillGroup` the runner learns that the leader has ended without reaping it: `waitid(WEXITED|WNOWAIT)` on the process's pidfd, which Go 1.27 hands out through `os.Process.WithHandle` (the process ID when there is none; it stays the child's until it is reaped). `os/exec` reaps only in `Cmd.Wait`, which is called after the group check, so nothing reaps the leader early. While the leader is held (a zombie, and the group's ID with it) the runner kills the group and watches it empty through `/proc`. Only then does it reap the leader (`group.reap`). Every signal to the group, including the context's SIGTERM from `Cmd.Cancel`, goes through `group.signal`, which sends nothing once reaping has started. A group still there after 30 s is reported as `*GroupLeftError` (wrapping `ErrGroupLeft`), joined with whatever else failed. That failure is the exit status taken from the `waitid` record, or the cancellation, and `Interactive` no longer turns the error into a nil exit. A watcher then keeps killing the group, reaps the leader when no member runs and closes `GroupLeftError.Gone`. In the daemon, `runPush` takes a `release` function (the box lock, the report files, the push note) and calls it after removing the quarantine, or, for a group left, leaves everything to `holdRelay`. `holdRelay` keeps the quarantine and the lock and marks the relay held, so `serveGit` refuses pushes with a message saying why (before taking the lock, and after a lock timeout). When `Gone` closes, it removes the quarantine, clears the mark and calls `release`. Tests: `execx.TestKillGroupLeft` uses real processes: a member that ignores the signal outlives its leader while the leader exits with status 3 or is ended by the context, through `Run` and `Interactive`. It asserts that the other failure and the group are both reported, that the leader is a zombie while the member runs, that `Gone` closes and the leader is reaped once the member is killed, and that no signal went to the group's ID after reaping. SIGKILL cannot be ignored, so the test makes the runner send SIGTERM in its place. Its control, a member that does not ignore the signal, gets the exit status alone, with the group gone and the leader reaped on return. `daemon.TestPushGroupLeft` covers the relay: with the group left, the error is returned, the quarantine stays, `release` is not called and the relay is refused while another relay is not. Closing `Gone` removes the quarantine, calls `release` once and lifts the refusal. Its control, a push without a group left, cleans up and releases before returning. `execx.TestKillGroup` and `daemon.TestPushEndedDuringIndexPack` are extended: they run unchanged on the new order, and `release` is called exactly once. `TestRelayService` was run as the integration test.

**F1-02 (`--as-of` and untimed generations) — fixed.** In `chooseGenerations` a generation without a completion time counts as older than every timed one. If a timed generation was completed at or before the time, the newest such one is restored as before. If none was and the file has untimed generations, it is chosen among those by the same rules as without `--as-of` (`chooseUsable`; an incomplete mutable one is not restored and is reported as incomplete). The file is then listed in the new `RestoreReport.AsOfUntimed`, which `state pull` prints as "restored from a generation without a recorded time". A file is left out as newer only when it has neither. Test: `fleet.TestRestoreAsOfUntimed` is the reviewer's scenario (untimed generation 0, generation 1 from Tuesday, pulled as of Monday: generation 0 is restored and listed, nothing is left out). It also covers a generation without any record, an incomplete untimed one of a mutable file and of an append-only file, and controls where a timed generation at or before the time wins and where an all-timed newer file is left out. `TestRestoreAsOf` still passes, and `TestFleet` was run.

**F2-01 (redirects of unchecked downloads) — fixed.** A `candidate` now carries `redirect`, the rule for where a redirect may lead. `download` applies it (through `client`'s `CheckRedirect`, at every hop) to every download without a checksum, and an unchecked candidate without a rule follows no redirect. Checked downloads keep the old rule, since their checksum covers wherever they end. CRAN's archive candidate allows only the same path (`samePath`; host and scheme may change, still under `allowedURL`). The GitHub tarball, the other exempt download, had the same weakness. It now allows only a tarball of the same owner, repository (both compared without case, as GitHub does) and commit, as `.../<owner>/<repo>/{tarball,tar.gz,legacy.tar.gz}/<sha>` (`sameTarball`), so a renamed repository is refused. Test: `depsrc.TestFetchRedirects` runs the reviewer's redirect of `mypkg_1.1.0` from the archive into `src/contrib/mypkg_1.2.0.tar.gz`, and one to another archived version. Both are refused before anything is downloaded, and nothing is cached. GitHub redirects to another repository, another owner, another commit, a zip, or a longer path are refused too. Controls: the same archive path with a query, GitHub's default redirect to codeload, and a mixed-case `legacy.tar.gz` redirect are all followed. The stand-in gained `CRANArchiveRedirect` and `GitHubRedirect`, and `TestDepSources` was run (GitHub's codeload redirect through the box).

**F2-02 (npm versions) — fixed.** `npmExact` replaces `npmExactRE`. Only the bare form `MAJOR.MINOR.PATCH[-prerelease][+build]` counts as exact: numbers without leading zeros and at most 9007199254740991 (also numeric prerelease identifiers, which is stricter than npm and so still a subset), identifiers of `[0-9A-Za-z-]`, at most 256 characters. The leading `v` and `=` that npm only normalises away are no longer exact. Everything else is resolved online, and `cachedVersion` and `rememberAlias` ignore and never write aliases for such names. Test: `depsrc.TestFetchMovingNames` (extended) moves the tag `9007199254740992.0.0` from 1.0.0 to 1.1.0. It is resolved online each time, no alias is written, an alias planted for it is ignored, and it is not answered without the registry. `v1.0.0` asks the registry every time while its tree comes from the cache, and a table covers the boundaries (2^53-1 against 2^53, leading zeros in core and prerelease, empty identifiers, other characters, 256 against 257 characters, and the 128-character limit of `CheckVersion`). `TestFetchCachedOffline` (extended) now shows the normalisation alias with `1.0.0+build.5` and lists `v1.0.0` among the names that need the registry. PyPI and CRAN were checked against the same idea, and nothing needed to change. Neither has tags or ranges in the URLs devc uses. PyPI's JSON API takes a version string to the one release it normalises to (PEP 440), a release keeps its version, and strings that name no release, such as `latest`, are not found. CRAN serves a version only under its own file name, as the current release (checked against `PACKAGES`) or in the archive, and never reuses a version. So any version string that resolves there names one release for good, and the existing `concrete` rule for them stands.
