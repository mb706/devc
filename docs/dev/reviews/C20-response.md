# C20: outcome per item

The confirmed defects of `docs/dev/LEFTOVER.md` part 7 that break the project's own rules, fixed in chunks C20a (high severity), C20b and C20c. Each fix has a regression test that fails without it; each limit is tested by exceeding it, with a positive control.

## C20a: the five high-severity items

**X6 3, journals without bound: fixed as decided.** `session.Store.ingestFile` appends only the leading events that fit three limits (`session.room.fits`): the session's journal within `sessions.session_journal_max` (default 128 MiB), the project's journals within `sessions.journal_quota` (default 2 GiB) and the free-space reserve that pushes keep (1 GiB, now `paths.StateMinFree`). Toward the quota each journal counts its size in whole 4 KiB blocks plus one block for the session's owner record (`session.journalCost`), so many small sessions use up the budget as one large one does. The rest stays in the spool. The host writes one note naming the budget and how to go on (`session.StopText`): not when the journal already ends with that note (the offsets were lost, or the box recreated its spool file), and never into a journal it would create for the note alone. The budget is kept in the file's offsets entry, and the file is not read again until the budget has room (an eighth of it, at most 1 MiB), so a stopped session costs one `lstat` and one `statfs` per run. Host events a box causes (`request`, push notes) are refused with `session.ErrBudget`; `session.end`, `seen` and `answer` always go in, so a stopped session can still be ended and pruned. Ownership is now claimed only when an event is appended: an empty spool file, or a new session while the quota is full, records nothing (before, an empty file claimed an owner record, which a box could repeat without bound). `devc sessions prune <project> --before <date or duration>` (new, `session.Store.Prune`) removes the journals of sessions that ended before the cutoff and their owner records, under the ingestion lock, never a live session and nothing without the flag; the daemon's journal follower drops the views of removed journals. `devc ps` warns and `devc doctor` has a check `journals` (`session.Store.Budget`). The project's total is counted from the directory at most every ten seconds per process, adding the process's own appends, and counted again before a refusal (recorded in LEFTOVER part 5). Tests: `session.TestJournalSessionBudget` (stop, one note, no second note after the offsets are lost, resume after raising, the journal's earlier bytes unchanged; control: a session below its budget whole), `TestJournalProjectBudget` (54 sessions and 50 empty spool files: total within the quota, no owner records for empty files or a late session, a box-caused host note refused, `session.end` accepted, prune by cutoff, ingestion goes on), `TestJournalSpaceReserve`; integration `TestJournalBudgets` with budgets of 32 KiB and 160 KiB set in project.toml (live fake sessions and spool-only ones, `ps`, `doctor --json`, prune without and with `--before`, raising the budget).

**X7 1, banking without a storage budget: fixed as decided.** `gitx.Service.fetchFromBox` checks the free-space reserve and `git.relay_quota` before git starts, runs the fetch with the new `Call.Group` (an `execx` process group ended and waited for as a whole, also from the command line) and under `gitx.Watch`, which is the push watchdog moved out of the daemon: `daemon.Daemon.watchPush` now calls it with the quarantine as measure, the bank with the growth of the relay's object store (`gitx.ObjectsUsage`; with `unpackLimit=1` a fetch only adds packs). Once git's processes are gone, an ended or failed fetch's temporary packs and lock files are removed (`gitx.RemoveFetchLeftovers`); a pack completed before the end stays and counts toward the budget. If the group outlives its wait, the bank keeps the box lock until it ends or the command's time is up, as `holdRelay` keeps a push's lock. A failed bank is a `NotPreservedError` with the reason; refs are written only below `refs/devc/incoming/`, so earlier bank refs are untouched. Tests: `gitx.TestBankFetchBudget` with real git (refused without the reserve and with the relay over its budget, nothing fetched; a 64 MiB commit with a budget of 4 MiB more ended by the watchdog: no temporary pack, quarantine or lock, bank refs and heads unchanged, no incoming refs, fsck passes; control: with room the next bank banks it); integration `TestBankBudget` (`git.relay_quota = "8m"`, a 40 MiB commit in a real box). `daemon.TestPushWatchdog`, `TestPushEndedDuringIndexPack` and `TestPushGroupLeft` pass on the shared watchdog.

**X7 2, banking fetches every ref a box offers: fixed as decided.** `gitx.Service.listBox` runs `git for-each-ref --count` in the box over `refs/heads/`, `refs/devc/wip/` and `refs/tags/`; a listing over 50,000 refs, truncated by the engine's output cap, with a line over 1,024 bytes or a ref outside those namespaces refuses the bank. Names that fail `names.CheckRef` (or the worktree rule) are reported as skipped and not fetched. `gitx.bankFetch` takes refs whose value the relay already records from the listing (a branch at its box tip or relay head, a snapshot equal to the last one, a tag equal to the upstream's or recorded; a relay ref points at their objects) and fetches the others by name, one exact refspec each on `git fetch --stdin`; no wildcard reaches git. More than 1000 (the bank policy's `DefaultMaxChanges`) changed branches, new snapshots or new tags refuse the bank before anything is fetched, with a message that names the limit. Decided within the table: the limit counts the refs a bank would fetch, not unchanged ones, so a box repository that holds an upstream's thousands of tags is still banked; the listing itself is bounded at 50,000 refs. Tests: `gitx.TestBankListsAndFetchesByName` (exact refspecs, no `*`; a bank with nothing new fetches nothing; one changed branch fetches only it; four changed branches over a limit of three refused unfetched and the relay unchanged, three banked; a listing over its bound refused, at its bound banked); integration `TestBankBudget` (1001 changed branches refused, the relay unchanged; banked once removed).

**X8 4, forwards without an admission limit: fixed as decided.** `netpolicy.Admission` is a counting limit that refuses at once and logs refusals at most once a minute with their number. `Forwarder.Serve` uses one of 64 places (`MaxForwardConns`) and closes a connection beyond that before any dial process starts. `Forwarder.Dial` takes a place from the Admission it is given; the router shares one of 256 (`MaxRouterConns`) across all boxes, which also covers the transport's idle connections, and answers `503` when it is full (the router's 128 request places stay). Tests: `netpolicy.TestForwarderAdmission` (64 connections served, three more closed at once with no process started and one log line; after one ends a new one is served; `Dial` with two places refuses the third with `ErrBusy` and admits again after one is closed).

**X9 1, a box pushes out the owner's savepoints: fixed as decided.** The daemon carries out a savepoint request as `devc save --request <id> -- [name] <project>`. `data.Service.SaveRequested` records the class `requested` and the request's ID in the index (`Savepoint.Class`, `Savepoint.Request`); the index is common to both drivers. After a requested save only `data.RequestedRetention` runs: the newest `data.savepoints.requested_keep` (default 10) requested savepoints stay, named or not. `data.Retention`, after an owner's save, counts and drops only the owner's unnamed savepoints; `devc data gc` applies both. A requested save inside `data.savepoints.requested_interval` (default 10 minutes) of the newest requested one is refused under the box lock with the reason; the daemon also refuses the request itself, with the reason, while another savepoint request of the project is outstanding or the interval has not passed (`requestService.savepointRefusal`). Decisions: savepoints recorded before classes existed count as the owner's (they were kept under the owner's rule, and counting them as requested would drop the owner's named ones); `before_session` counts only the owner's savepoints, as a box requesting a savepoint every ten minutes would otherwise stop devc's own before-session savepoints and have them dropped by requested retention later; both limits are configurable (positive values only) so the integration test can be fast; `devc data ls` shows the class. Tests: `data.TestRequestedSavepoints` for restic and reflink (a reflink worker answering as on a cloning file system): legacy, named and unnamed owner's savepoints survive four requested ones with `requested_keep = 2`, the requested name "keepme" goes, requests inside the interval are refused, the owner's retention does not count requested ones, `before_session` takes its own savepoint after a requested one, and reflink copies are dropped by ID; `daemon.TestSavepointRequestWindow` (refused while one is pending and inside the interval, the owner's own savepoint not counted; control: accepted after the interval); `daemon.TestRequestCommands`; integration `TestRequestedSavepoints` (restic, a real daemon and box, interval 15 s).

## C20b: the rule violations of medium severity

**G1-01, the capability record is rewritten for a running box: fixed as decided.** The only writer of the record is `box.Manager.recordCapabilities`, called only from `afterStart`, which only `createAndStart` and `startStopped` call, after `publish` removed the old record and marker; `up`'s branch that finished the start of a running box without its marker is gone. Every command that finds the box running goes through `box.CheckStarted`: the readiness marker must be there and the record must belong to the running container ID, else `box.UnfinishedError` names what is missing and asks for `devc down` and `devc up`. `up` (also `--all`), `ensureRunning` (`sh`, `run`, `root`, `devc <harness>`, `wt`, `forward`, `editor`, `gui up`) and the daemon's session start (`commander.startRefusal`, with the watched container ID) use it; the level-internet check still comes first, so a running box without its rules is restarted properly as before. Thinking as the box: deleting the marker now only blocks its own commands; writing it back makes the box usable as it was started; it cannot reach the record, which sits in `local/boxes`. A healthy running box is "already running" as before; after a host reboot the container is stopped, so `up` starts it and writes a new record. Decided within the table: a running, ready box without a record for its container (started by an older devc, or with plain `podman start` after `down`) is refused too, since it is the same "start that did not finish" and gets nothing on demand anyway. Tests: `box.TestRunningButNotReady` (rewritten: a grant added while the box runs; ordinary case used; marker removed, a record of another container, no record: `up`, `run`, `root`, `sh`, `WithRunningBox` refused with the restart advice, nothing exec'd, box left running, record unchanged; control: after `down`/`up` the record has the new grant), `daemon.TestStartAndStop` (session start refused without a record and without the marker, no exec, no record written; control: started).

**X4 2, `devc login status` prints a container's output raw: fixed as decided.** `harness.LoginRunner.Status` returns `proto.PrintableText` of the output. The interactive login (`LoginRunner.Interactive`) now routes the container's stdout and stderr through the new `proto.PrintableWriter`, the streaming form of the same escaping: control and format characters become U+FFFD, a UTF-8 sequence split between writes is kept whole, and CR passes only directly before LF, as a terminal ends lines (podman with `-t` and a piped stdout was tried: it sends the pty's CR LF; the host terminal is in raw mode). Consequence, recorded in the guide: a vendor login's colours and cursor movements show as `�[…`; the built-in logins print a URL or a code, which stay readable. Tests: `harness.TestLoginOutputEscaped` (a clipboard escape, a screen clear, a bell and a lone CR in status and login output), `proto.TestPrintableWriter` (byte-by-byte, two-byte and three-byte writes).

**X6 2, a panic in a stream handler ends the daemon: fixed as decided.** One function, `daemon.recoverTask`, used by `goSafe` and the new `goTask`; every goroutine of the package starts through one of them (raw streams via `acceptStreams`, the copies of git, gate and dial streams, the push watchdog and the held-relay waiter, `projects.list` workers, subscribers, hub-link pingers and roles, terminal ends, `daemon.stop`, the waiters). The log carries the box, the method (a stream's method once its first line is read) and the frames without arguments (`proto.PanicSite`), and the panic's value only for a `runtime.Error` (`proto.PanicText`), so nothing a handler held can be logged; `proto.Conn`'s own recovery now logs the same way. Then the task's `end` closes that stream (abort), fails that request (`projects.list` answers "internal error"), or closes that connection. What a goroutine held is given back by deferred calls: the stream's pending place (now released by a deferred `sync.OnceFunc`), relay and request places, the box lock of a push (`runPush` releases it on a panic before it was handed on; the release closure releases the lock even when the report panics), a service login flight and a worktree read in progress (both now ended in a defer, so waiting requests go on). The HTTP servers of services and local URLs, whose error logs are discarded, wrap their handlers in `recoverHandler`, which logs through `recoverTask` and aborts that connection (`http.ErrAbortHandler`). Tests: `daemon.TestNoBareGoroutines` (parses the package: no `go` statement outside `goTask`/`goSafe`), `TestBoxStreamPanic` (40 `host.git` streams whose git panics with a secret in the value: each stream ends, more than the 32 places, then a request and the daemon still answer; the log names box, method and `serveGitProcess` and not the secret; fails, by crashing the test binary, with the old bare `go`), `TestPushPanicReleases` (control included), `TestProjectsPanic` (failing request, then a normal answer; the worktree read is not left loading).

**X7 3, the update hook leaves records for updates git then refuses: fixed as decided.** `gitx.Service.RecordUpdate` writes the bank ref or tag record and, in the same transaction, a marker `refs/devc/pending/<kind>/<name>/<time>`; it no longer moves the box tip. A record with a marker counts for nothing: `SortRefs` leaves it out of `LastBank`, `NewestTag`, `DevcTags` and `DevcTagNewest` (so banks and `devc push --tag` ignore it) and `Relay.ArchiveRefs` does not archive it. `gitx.Service.SettlePush` settles every marker: applied when the branch's tip is the record's object or its reflog (the relay logs every ref update) holds it, or the tag points at it; an applied record loses its marker, a refused one is deleted with it (old values checked), so nothing keeps the name. Box tips move there, for the push's branch records (from the `.records` note) whose applied tip is the box's own (`.heads` note). The daemon settles after receive-pack has ended, inside the release that runs before the box lock goes (`daemon.Daemon.settlePush`), and before it starts receive-pack (records a crashed daemon left); `Bank` settles first, as the table asks. The rule "recorded before accepted" is unchanged: the record exists, durably, before git applies the ref. Decisions: deleting a refused update's record is the one exception to "records are never deleted", stated in the invariant; the box tip moves only at settling (an applied push is the observation; a crashed daemon leaves it to the next bank's observation); a reflog scan is bounded to 1000 entries. The finding's claim was tried with real git 2.47 in the toolchain container: git does run the update hook for `refs/heads/main/<t>` while `main` exists and refuses the ref afterwards. Tests: `cli.TestRelayHooksSettle` (real receive-pack with devc's hooks: the refused `main/<t>`'s record is pending and ignored, settling removes it and `refs/devc/bank/main/<t>` can then be created; unsettled records of two accepted pushes, one superseded, are confirmed by tip and reflog, a refused one removed), `gitx.TestPendingRecords` (ignored by RefSet and the archive, removed by the next bank), `gitx.TestRecordPush` (box tips at settling).

**X12 6, the web app settles a waiting prompt from a box-written event: fixed as decided.** `settleOutbox` only marks the first waiting prompt whose whole text the event's is (trimmed; a truncated event may match a prefix) as `seen`, shown beside it ("a prompt like it is in the session (the receipt decides)"); it never removes the outbox entry or the pending command. `setOutbox` now takes a prompt out eight seconds after its final receipt, delivered included (before, a delivered prompt waited for its prompt event). ## C20c: gaps the accuracy review found

**G4-01, a seal recorded for a file the box can still write: fixed as decided.** `boxside.DataWorker.seal` opens a regular file once (`openData`) right after the type check; whether it is sealed already, its new owner and mode (`ownOpen`, through the descriptor) and its digest (`digestOpen`, read from the same descriptor) all go by that descriptor's `fstat`. The final check compares the name's `lstat` with the descriptor's device and inode, as it already did for directories; on a difference the seal fails with no record and no digest. Order of operations: lstat (type) → open → fstat → fchown/fchmod → lstat of the name vs the descriptor → digest from the descriptor → record. Thinking as the box: once the check passes the inode is the vault's, without write bits, in a sticky zone the vault owns, so the box can neither replace the name nor write the file (a descriptor it opened for writing before the seal still works, as the page already says). Test: `boxside.TestDataSealSwap`, with the new hook `sealHook` (as `statusExpireHook` elsewhere): B swapped in for the open and A put back before the check → refused, no `seals.jsonl`, A still the box's and writable, B sealed where it went; B left at the name → B sealed and its content digest recorded; control: a plain seal whose descriptor digest equals `digestEntry`'s. Fails against the old comparison with the first `lstat` (checked).

**G4-02, G4-03, `token:<secret>` can name any realm secret: fixed as decided.** One lookup, `config.Config.reservedSecret`, says what is reserved in a realm: `github-token`, the realm App's `key_secret`, every service's `CredentialSecrets()` (header `value_secret`, cookie login secrets) and every `_jar.` name. One guard, `config.Config.checkBoxSecret`, is the only place a name for delivery to a box is checked; its callers (all in `config.validateProject`): each `grants.secrets` entry, each harness credential (manifest `auth.secret` and the realm's `[harness.<id>] secret`), and `grants.github = "token:<secret>"`. `validateGitHubSecrets` and the credential and `_jar.` checks of `validateServiceGrants` are gone (subsumed). The service definitions use the same lookup through `config.Config.checkServiceSecret` (from `validateServices`): `value_secret` and `auth.secrets` may not be the GitHub credential, the App's key or a jar. Decided within the table: a service's credential is reserved for every project of the realm, granted the service or not (a box holding it gets past the service's rules); two services may share a credential (neither hands it to a box). The delivery paths themselves (`harness.BoxHooks.deliverSecrets`, `daemon.Daemon.secret`, `daemon.Daemon.githubToken`) refuse a project with configuration problems, so validation is where it holds. Tests: `config.TestReservedSecrets` (token: naming each of the four kinds, a service credential in `grants.secrets` of a project not granted the service, three service definitions; controls: a token in its own secret beside a service, two services sharing a credential), `TestGitHubSecretsNotGranted` and `TestBrokenServices` (the "credential granted too" case now reports `grants.secrets[0]`).

**G3-01, G3-19, `devc wt rm` deletes what nothing preserves: fixed as decided.** Reproduced first: `TestWorktreeRemoveUnpreserved` failed against the old code (bookworm's git deleted `.env.ign` without `--force`). In the box, `boxside.Repo.Unpreserved` lists ignored entries (`git ls-files --others --ignored --exclude-standard --directory`, so an ignored directory counts once; the worktree's `data` symlink is left out) and what `snapshotSplit` (the snapshot's own classification, moved out of `snapshotOne`) leaves out. `RemoveWorktree` returns a `WorktreeRemoval` report: without force it refuses when the worktree is dirty or anything is unpreserved; with force it removes and counts. `devc box worktree rm --json` prints it; `gitx.Service.WorktreeRemove` decodes it strictly (at most `MaxLostReported` = 20 names, total ≥ names), cuts each name to 300 characters and applies `proto.Printable`; the CLI prints the refusal (`WorktreeRemoval.RefusalText`) or "removed … with N files or directories that no snapshot kept". The help text says what a snapshot keeps; without a relay `--force` also loses uncommitted changes (said, unchanged). The harness worktree hook's `remove` uses the same refusal. Tests: `boxside.TestRemoveWorktreeUnpreserved` (26 entries, 20 listed, count; large file and nested repository; forced removal counts 2; control: only the data link), `TestWorktrees`, integration `TestWorktreeRemoveUnpreserved` (63 ignored entries including a directory and a name with an OSC 52 escape: refused, escaped, bounded, files kept; `--force` says 63; an 11 MiB untracked file; control: a plain worktree).

**G4-17, no savepoint before sessions the daemon starts: fixed as decided.** `devc save --before-session` (new flag, set by the daemon) runs `app.beforeSession`, the code `devc <harness>` uses (`saveBeforeSession` now calls it). `daemon.commander.runStart` calls `commander.saveBeforeSession` after `startRefusal` and before `delivering`: when the project has data and `before_session`, it runs that child with `runChild`. Bounds: the CLI's path runs under `lifecycleTimeout` (3 h) with the user at the terminal; the daemon's under `beforeSessionTimeout` = `requestTimeout` (30 min), the bound a requested savepoint has. Meanwhile the command stays `accepted` (nothing typed, only that start's goroutine waits; other commands go on; the box lock is the child's). A failed savepoint refuses the start with the end of the child's output; a timeout refuses it with "took longer than 30m0s … take one with 'devc save …', then start it again" (the child gets SIGTERM, then SIGKILL, like any timed-out child: a reflink or restic save it ran may leave its partial state, see LEFTOVER part 5); when the daemon stops meanwhile, the start stays accepted and is carried out after the restart. The CLI path through the daemon (`devc <harness> --prompt`) saves first, so the daemon's child finds a recent savepoint and does nothing. With the driver `none` nothing is taken; the guide says so. Tests: `daemon.TestStartSavepointFirst` (failed and timed-out savepoint refuse with the reason and no start in the box; taken: started; control without `before_session`: no child), integration `TestData` (a `save --before-session` with a recent savepoint takes none).

**G4-15, a service body without a declared length passes `max_body`: fixed as decided.** `svclogin.Proxy.ServeHTTP` reads a body with `ContentLength < 0` whole before the credential is fetched (`readBody`: through a limit of `max_body`+1, in memory up to 1 MiB, beyond that in a temporary file removed at once; the read has `limits.timeout` as read deadline). **G2-01, an error shows a box the host's path to its data root: fixed as decided.** `data.NormalizeInBox` (the box's request path) accepts only the in-box data root and names only it; `requestService.create` uses it. **G5-06, a failed `terminal.open` leaves the stream open: fixed as decided.** Hub (`hub.Server.apiTerminal`, the HTTP handler's goroutine): the deferred `terminal.close` is installed before `terminal.open` is sent, so it goes out on every path; after a valid answer it calls the new `terminal.confirm`, and a failed confirm ends the relay. Decided: the hub link's protocol number stays 1; a machine with this devc ends the terminals of an older hub after 30 s (LEFTOVER part 4).
