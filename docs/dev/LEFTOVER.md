# Leftover checks and open work

This is the list to work from when devc meets real accounts and other machines. It was consolidated at the end of the project (chunk C19r2) from the notes every chunk left, and updated by C19r3 and C19r4; items that a later chunk closed are gone, everything else is here. Nothing below has been verified unless it says so. "Tried here" means: on the development host (Ubuntu 24.04, rootless Podman 5.8.3 with slirp4netns, fuse-overlayfs and runc, cgroup v2 with cpu, memory and pids delegated, AppArmor user-namespace restriction, no SELinux, no KVM, amd64), always against fakes, stand-ins and local servers.

Parts: 1. to verify with a real login · 2. to verify on another kind of machine · 3. to set up before first real use · 4. decisions waiting for you · 5. known limits that are accepted · 6. deferred work.

## 1. To verify with a real login

No harness has ever been logged in, no real GitHub account or App, real service, real registry or real cluster was contacted. The test harness (`fake`) and the stand-ins cover devc's side; the vendor side is assumed from documentation (as of 2026-11). For each harness: install it (`devc harness install <id>`), log in (`devc login <realm> <id>`), and use a scratch project at network level `internet` unless a step says otherwise. Watch `devc ps`, `devc events <session> --json` and the daemon's log while you go.

### Services (a real upstream)

1. **Header service.** A wiki or API with a token of at least 8 characters (shorter ones are refused since C19r2). Correct: requests the rules allow work from the box, others get 403 with the needed rule, the token never comes back in headers. Since C19r4 the stored value is used without surrounding spaces, every word but a leading scheme (`Bearer`, `Basic`, `Token`, `Bot`, `Key`, `ApiKey`, `Api-Key`, `SSWS`, `OAuth`) must have 8 characters, and control or non-ASCII bytes are refused: check that the real token's format (for example a scheme devc does not list) passes `devc service status`.
2. **Cookie service.** Copy `examples/services/intranet`, adapt `login.sh` to the real form (CSRF tokens, redirects through an identity provider), `devc service login`. Correct: the jar is stored (cookies shorter than 8 characters are left out by the example script; a site whose session cookie is shorter cannot be used), requests carry the session, expiry or a redirect to `login_path` marks "needs a login", `auto = true` logs in again once, and a path that none of the cookies applies to (a cookie with a narrower `path`) goes out without a `Cookie` header (C19r4). Real servers' HTTP/1.1 and HTTP/2 framing were only tried against Go's test server.

### Registries for `devc src` (real network)

1. In a box with network: `devc src r:jsonlite`, `pypi:requests`, `npm:@types/node`, `github:cran/git2r@0.36.2`, then the same with explicit versions. Correct: each downloads, unpacks below `/src/<eco>/<name>/<version>/`, and a repeat with an exact version answers from the cache without network, while `npm:<pkg>@latest` asks the registry every time (C19r4). Since C19r2 a missing checksum is refused: check that PyPI's `digests.sha256`, npm's `dist.integrity` (or `shasum` for old packages) and the `MD5sum` of CRAN's `PACKAGES` are really present for ordinary packages; archived CRAN versions and GitHub tarballs are downloaded unchecked by design, and since C19r5 their redirects must keep to the archive path, or to the same owner, repository and commit (check that `github:cran/git2r@0.36.2`, which GitHub sends on to codeload, still comes). Since C19r4 CRAN's whole `PACKAGES` must parse (a malformed line, a line over 1 MiB or a package listed twice stops every CRAN download): check that the real index parses, and that an older version such as `r:jsonlite@1.8.0` comes from the archive.
2. At level `allowlist` with the presets `cran`, `pypi`, `npm`, `github`. Correct: the downloads pass the proxy (the presets are hand-written; a missing name shows in `devc net log --denied`).

## 3. To set up before first real use

### Host

1. **Rootless Podman** with subordinate IDs, `nsenter` (util-linux), git, rsync (keep it current: a hostile remote rsync could try receiver bugs such as CVE-2024-12087), OpenSSH ≥ 7.8 for the SSH gate. Run `devc doctor` and work through what it reports.
2. **cgroup delegation** of `memory` and `pids` (boxes) and `cpu` (the desktop's CPU limit, new in C19r2). Without it every box needs `memory = "none"` and `pids = -1` under `[box]`, and the desktop `memory = "none"`, `pids = -1`, `cpus = -1` under `[gui]`, set explicitly.
3. **Storage driver.** On the development host fuse-overlayfs 1.17 with libfuse 3.18.2 hangs in `statx()` with the birth-time mask; it breaks `apt-get update` on Debian trixie and is expected to hang Claude Code. `devc doctor overlay-statx` detects it. Use native overlay (`mount_program` unset in `storage.conf`) or another fuse-overlayfs (decision in part 4).
4. **The daemon as a service**: `devc service install`, and `loginctl enable-linger` (root) for the daemon and timers to run while you are logged out.
5. **Images.** The example envs `r-base` and `python-base` were never built (`r-base` uses `COPY --chmod`, which needs a recent buildah); the example `base` env and the installer image use Debian bookworm (trixie was never built on a healthy host). The desktop image is built on the first `devc gui up` (network, about 470 MB).

### Accounts and secrets

1. **Harnesses**: `devc harness install <id>` and `devc login <realm> <id>` per realm (part 1).
2. **GitHub**: the host credential (`devc secret set <realm> github-token`, or `gh auth login`). For `grants.github = "app"`: create the App (repository permissions as needed, Workflows "No access", installable only on your account), generate a key and store it with `devc secret set <realm> github-app-key < key.pem`, install it on the repositories, add `[github.app]` with `app_id` (and optionally `installation_id`) to `realm.toml`. Protect default and release branches with a ruleset (restrict deletions, block force pushes, require a pull request; you, not the App, as bypass actor). The steps are in `docs/guide.md` and were never walked through.
3. **Services**: header credentials and cookie values must have at least 8 characters (C19r2).
4. **Remotes**: `[data.remotes.<name>]` per project, `machine_name` in `config.toml` if the host name is not what you want in the manifest.

### Hub

1. Follow `docs/hub-deployment.md`: `devc hub init --public-name …`, TLS (direct, or behind nginx or Caddy as described; the proxy configurations were checked by a script with nginx 1.28.0 and Caddy 2.10.0, Caddy's logging rule only validated), the CA and its backup, `devc hub user`/`set-password`/TOTP, device enrolment (PKCS#12 bundles), machine joins, the ntfy server and topic, `hub.toml [archive]` quotas. A server certificate from a public CA is read at start: renewing it needs a hub restart (behind a proxy, the proxy renews).
2. A second hub needs the same CA (`devc hub init --ca-from`, `devc hub ca import`), its own database and its own ntfy topic; hubs and machines are upgraded together.
3. Every enrolled machine can read every machine's archive of realms; a machine refuses realms it is not configured for (by design, documented).

### If you used devc during development

Boxes keep what they were started with. After upgrading to C19r2: restart every box (`devc down`, `devc up`) — token modes are refused for boxes without the new `github_upstream` in their start record; boxes created before C16 need `devc up --recreate`; restart the daemon; log in to cookie services again if a stored jar has cookie values shorter than 8 characters; store longer header credentials if `devc service status` says `invalid-secret`; service rules with percent-encoded reserved characters are now configuration problems (write the characters unencoded); older pull records have no remote digest, so `devc data status` marks their remote with `*` until the next pull.

After upgrading to C19r3: upgrade the hubs together with the machines (generations completed on an older hub have no completion time, so retention keeps them; `state pull --as-of` takes a file with only such generations as it is now, and since C19r5 restores such a generation, listed separately, when every timed generation of the file is newer); restart the daemon; reload the web app (new service-worker cache).

After upgrading to C19r4: a desktop that runs from before is refused by `devc gui up` (it recorded no limits or image generation) until `devc gui up --restart` replaces it; pull records from before C19r4 have no outcome, so `devc data status` does not show their remote as matching until the next pull; a header credential stored with control characters or non-ASCII bytes is now refused (`devc service status` says `invalid-secret`), one with spaces around it is used without them; restart the daemon for the service changes. Alias files that an older devc stored in `/src/npm/...` for dist-tags (`.alias-latest`), and since C19r5 for names npm does not take for versions (`.alias-v1.2.3`, numbers above 9007199254740991), are ignored and may be deleted.

## 5. Known limits that are accepted

### Isolation and realms

- A realm is one trust domain: boxes of a realm share harness state, memory, the package cache, the source cache `/src` and shares, and one box can influence the others (a box-writable shared home can plant Codex hooks or MCP servers that run in other boxes and in the shared-home login container).
- Per-box mount points inside a realm-shared harness home are created without following links just before the start; another running box of the realm can still swap a component between that check and the engine's mount.
- The nested-mount-point check and `box fix-identity` run on starts through devc only; a container recreated outside devc lacks them (`/etc/shadow` is never updated).
- Sealing protects against the box only: a descriptor opened for writing before the seal keeps working; FIFOs, sockets and devices inside a sealed entry are skipped; a hard-linked file is sealed under every name; a worker killed half-way leaves a partly sealed entry (sealing again completes it).
- restic exit status 3 still records the savepoint with a warning (files the box made unreadable are missing); restic prunes only in `devc data gc`.
- A box can make the host store as much as it pushes within `git.relay_quota`; index-pack and fsck of a large pack use the host's CPU and memory unlimited for a while.
- Host public addresses are rejected as they were at the box's start; an address the host gets later is covered after a restart.
- Text from boxes (`devc ps --json`, journals, notifications) is escaped for terminals but must be treated as untrusted by other consumers.
- Codex's `developer_instructions`, `check_for_update_on_startup` and `cli_auth_credentials_store` cannot be enforced by requirements; they are managed defaults a box could weaken for the realm through the shared home if Codex drops that layer.
- The binding check compares PID 1's start time as the host and the box see it; a box with a time-namespace offset would fail closed at every start (Podman gives containers none).

### Network

- At level `internet` DNS to the trusted resolvers is a channel (tunnelling through queries is possible); the canary tests one TCP port per address, the rules cover the rest.
- At level `allowlist` the allowlist limits names, not content: an allowed relaying host can receive anything; domain fronting through CONNECT cannot be detected; IPv6-only upstreams are unreachable; tools that ignore the proxy variables have no network.
- Local URLs share the parent name `localhost`, so one box's page can set cookies for another's local URL; router origins are strict (no cross-origin grant).
- The router listens on `router.listen` as it was at daemon start.

### Git and relays

- Git over `connect` uses protocol v0 (every visible ref is advertised); no partial clones.
- Relays are never repacked (`gc.auto = 0`, every push its own pack since C19r1), bank refs and box tips are never pruned, deleted upstream tags are kept.
- A bank applies at most 1000 branches and 1000 tags per run; the push watchdog measures every 200 ms and may overshoot the budget by that much.
- Since C20a a bank is refused, before anything is fetched, when the box offers more than 50,000 refs (branches, snapshot refs and tags, changed or not; a box repository holding a very large upstream's tags counts them all), a listing larger than the engine's 8 MiB output cap, or more than 1000 changed branches, new snapshots or new tags (it no longer banks the first 1000 and defers the rest). A pack the fetch completed before the watchdog ended it stays in the relay and counts toward its budget.
- A bank's fetch whose git processes cannot be ended within 30 seconds keeps the bank waiting, with the box lock, until they end or the command's time is up (C20a); there is no held-relay mark as for pushes, so a push meanwhile waits for the lock and then says devc is busy. Not testable here (no process can ignore SIGKILL).
- Only the daemon's git commands, and a bank's fetch from a box wherever it runs (C20a), run in a process group of their own that is ended with everything they started (C19r3); other git run by a command-line command stays in the terminal's foreground group, which an interrupt ends, and is not waited for if devc itself is killed.
- A push whose git processes cannot be ended within 30 seconds (stuck in the kernel) keeps the relay's lock and quarantine and refuses pushes until the last of them has ended; meanwhile other devc commands on that box wait for its lock, and the daemon keeps the group's leader unreaped (C19r5). If the leader could not even be waited for without reaping it (never seen), the relay stays held until the daemon restarts. No test can make a process ignore SIGKILL: the runner's test stands one in with a process that ignores the signal sent instead.
- Old box agents break pushes whose receive-pack takes longer than a minute after the pack (until the box restarts).

### Data and sync

- Every pull transfers the selected files in full (the host may not read the data tree to compare); a continued pull also brings what the interrupted one received.
- A push decides by size and modification time, which the box controls; staged files are hard links that a process holding one open can still change; the box can block pushes by creating `.devc-staging` (the push refuses).
- A pull trusts the remote's rsync (receiver bugs); rsync ≥ 3.0 is needed on the remote.
- One pull or push per project and remote at a time; a second is refused, not queued (C19r2).
- A preview whose listing is cut (over 256 MiB) or has a line devc does not know is refused; pull fewer paths at a time (C19r2).
- A pull or push records at most 100,000 entries (direct children of the zones named, and the other paths), and fewer when their names are long or need much escaping (the worker's report of 64 MiB must hold them); a pull above that is refused before the transfer and again before the merge, a push before staging (C19r4). `data status` of a project with more than 100,000 top-level entries fails for the same reason.
- `data status` compares a remote with what a pull received from it, and only a pull that merged the entry completely can match (C19r4: not one that left a sealed entry alone or left a special file out, even with equal listings); after a push it can only say that the remote received the entry as it is now (`>`), since devc never deletes on a remote and does not list it afterwards (C19r2). Digests list names and sizes: a later change that keeps every file's name and size still shows the entry as recorded and the remote as matching (`devc data verify --content` compares contents).
- The manifest is not rotated; above 10 MiB the context worker leaves it out of commits.
- A pull and a push with different remotes may run at once (separate staging directories, the box lock only for worker phases); that was never run concurrently in a test.
- A project directory whose `.devc` the box created (possible before C06) is refused by setup until you move it away; an in-place restore does not reset the mode of a directory that still exists.

### Sessions, harnesses and input

- Journals are never rotated; they are bounded by `sessions.session_journal_max` and `sessions.journal_quota` and removed only by `devc sessions prune` (C20a). Diff snapshots leave unreachable objects in the context repository.
- Journal budgets (C20a): each devc process counts the project's journals from the directory at most every ten seconds and adds its own appends, so appends by another devc process meanwhile can take the total past the quota by what that process appended (each process checks its own fresh count). A session stopped by its own budget stays stopped until the budget is raised by at least an eighth (at most 1 MiB); its later events, its `session.end` included, stay in the spool, and only reconciliation (lost) or `devc down` ends it. A box-caused host event (a request's journal event, a push note) that does not fit is not recorded in the journal; the request itself is in the request log. What the spool keeps meanwhile is bounded only by the runtime directory's file system.
- Forward admission (C20a): 64 connections per forward and 256 dial processes for the router are fixed, not configurable.
- Requested savepoints (C20a): the daemon refuses a savepoint request at once while another is outstanding or the last requested savepoint is younger than `requested_interval`; the authoritative check is in `devc save --request`, under the box lock, so a request that passes the first check can still fail there. Savepoints recorded before C20a have no class and count as the owner's, also those a box requested.
- Program Status Protocol choices: only 7-bit `ESC ]` is recognised; a possible report start at the end of output is held up to 30 ms; child records and `progress`/`title` are dropped.
- Flooding a terminal through `podman exec -t` with output the program echoes back can deadlock conmon (tmux, the real outer terminal, is not affected).
- The wrapper is used only when the launcher has a terminal; receipts keep a command's text until it is final, and a queued command older than seven days is refused.
- `session.start` needs a running box; the CLI creates worktrees, the daemon does not.
- The daemon keeps the derived view of every session it has read; subscriptions more than 4096 batches behind are disconnected.
- tmux refuses `send-keys` while a read-only client is attached to its most recently active session; devc's own terminal clients are no longer read-only (C19r4), but a box that attaches a read-only client of its own makes devc's typing into it end `unknown` (text pasted, submit key refused).

### Daemon and channel

- The agent's host check assumes the box never shares the host's PID namespace.
- A box that deletes `/run/devc/agent.sock` cuts itself off from the daemon until it restarts.
- Raw streams end after a 2-minute write stall (a suspended SSH client through the gate loses its connection); channel budgets were set by reasoning, not measurement.
- A `config.toml` that does not parse makes the running daemon drop its hub list until it is fixed.
- Spool warnings the daemon meets on its own go to the next client that asks (the daemon's log has them all); without a daemon nothing in `devc requests` expires.
- The SSH gate runs `devc gate-exec` through your login shell: a `nologin` shell disables the gate, and start-up files that print something corrupt sftp and scp (only zsh was tried). A grant added while a box runs needs `devc up --recreate`; a regenerated gate host key makes running boxes refuse the gate until they restart.

### Hub and web app

- A compromised machine can fill its own part of the hub up to the limits (sessions, events, archive quota) and archive garbage under its own name; it cannot touch other machines' data.
- Rate limits count HTTP failures only (not TLS handshakes in direct mode); behind a proxy without `X-Real-IP` every client is one address; five wrong passwords lock a certificate's logins for 15 minutes.
- Direct TLS serves HTTP/1.1 only; a slow browser loses the terminal stream after 512 queued messages; the terminal follows the window size every 5 s and lives at most 12 hours; a crashed daemon leaves the box's grouped tmux session until the box restarts; the terminal may show another window of the same box briefly when the observed one is killed.
- Hand-over between hubs can notify twice rather than lose a notification.
- Ended sessions older than 30 days are pruned and no longer listed; paging backwards relies on consecutive event numbers, and once the screen pages back it stops following live events (it shows how many are newer) until **Back to the latest**; a duplicate session ID in two projects of one machine (only from before C12r1) shows as the project learned first.
- The hub reads its CA key to sign enrolment requests; `set-password` keeps existing login sessions (it points to `devc hub sessions revoke --all`).
- The terminal's styles need constructable stylesheets (Chrome 73, Firefox 101, Safari 16.4); `projects.list` asks every running box for its worktrees (slow with many); a session outside a worktree shows main's changes; a pending command is polled every 10 s while its machine is online.
- The development mode (`--dev-no-auth`, only with `DEVC_DEV=1`, loopback) is a server without authentication while it runs.
- Vendored web files are checked against recorded checksums, not signatures.

### GitHub

- In token modes the token can do on GitHub whatever its permissions allow, beyond the relay's branch rules; a minted token lives up to an hour, and a long-running process keeps the `GH_TOKEN` it started with.
- `grants.github_read` matches repositories by name; renamed or transferred repositories keep what the configuration says.
- Facade budgets (120 reads and 120 token requests a minute per project) share GitHub's limits with your other tools.
- The installation check is cached for up to 24 hours per project, key and repository (forgotten at once when a mint fails) (C19r2).

### Services

- A service acts with your account for every request its rules allow; an upstream that reflects request headers in its body shows the credential (only headers are scrubbed).
- One request per connection; exchanges longer than `limits.timeout` plus a few seconds are cut, also on the box's side (C19r2): raise the timeout for long downloads.
- Credentials and cookie values shorter than 8 characters cannot be used (C19r2); a site whose session cookie is shorter cannot be a cookie service. Every word of a header credential except a leading scheme from devc's short list counts (C19r4): with a scheme devc does not list, the scheme word itself must have 8 characters and is scrubbed from responses like the secret.
- Logins run without a terminal (no second factor typed in) and without a browser.

### Shares and sources

- Shares put published text in front of every agent that lists them; boxes see earlier versions below `/opt/shares/.v/<name>/`; `export-ignore` in `.gitattributes` can make a share smaller than its preview.
- The source cache is writable by every box of the realm and never pruned; two concurrent fetches of one version both download.
- CRAN's archived versions and GitHub's tarballs are downloaded without a checksum, because none is published (C19r2); a redirect is followed only to the same archive path, or to a tarball of the same owner, repository and commit, so a renamed GitHub repository must be named by its new name (C19r5). A CRAN version that is not the index's current one is taken only from the archive, so for the moment between a release and the next index update it is not found (C19r4).
- npm dist-tags and ranges, GitHub branches and tags, and "the current release" always need the registry; only exact versions and commits are answered offline (C19r4). An npm version is exact only in the plain form npm takes for a version, so `v1.2.3` asks the registry every time (C19r5).
- Installed versions are found through the usual places only (no pipx/uv tool environments, npm's global prefix or `direct_url.json`).

### Desktop

- The cookie is readable in the box on purpose: anything in the box can drive and read the display and see what you type or paste into the viewer; the clipboard crosses both ways.
- A box can exhaust its own desktop: the X relay serves 64 connections and the viewer's server 16 at a time, and TigerVNC refuses further unauthenticated VNC connections from 127.0.0.1 after five (its blacklisting, seen in C19r2), so a box holding VNC connections can keep the viewer out for a while. It cannot reach beyond its desktop's limits (`[gui]`).
- Stale sidecars of a box stopped outside devc run until `gui down`, `down`, `rm` or the next start.
- A running desktop created with other `[gui]` limits or another image generation (or whose record devc lost) is refused by `gui up` until `--restart` replaces it, never replaced silently (C19r4). `gui build --rebuild` (a security update of the same build files) does not change the generation, so a running desktop keeps its older image until `--restart`.
- The image is about 470 MB (Mesa and LLVM through libgl1, NumPy, Perl).

### Fleet and archive

- Generations of append-only files are rate-limited to one per hour per file; mutable-file snapshots take up to `[sync] max_file_size` per file and hub while uploading.
- Restores stage whole bundles and imports extract the whole export first (up to twice the archive's size on disk); the hub walks a machine's archive once per start to count usage.
- Restored journals appear as sessions of the restoring machine; `--merge` keeps the local `main` of the context repository.
- Generations without a record (archives from before C19r1) are restore candidates at their stored length, decided generation by generation; generations completed before C19r3 have no completion time, so retention never drops them; `state pull --as-of` counts them as older than every timed generation (a file with only such generations is taken as it is now; one whose timed generations are all newer gets its newest such generation, listed as restored from a generation without a recorded time, which may be newer than the time asked for; C19r5). Upload bookkeeping started over once with state version 2.
- A mutable file keeps up to `3 + keep_daily + keep_weekly` complete generations on each hub (space for the retention window). Retention follows the hub's clock: while it is behind a time it recorded for a file nothing of that file is dropped; a clock that ran far ahead and recorded future times pauses retention of those files until real time catches up.
- `state pull --as-of` restores journals and logs from the generation in use at that time, with what was appended to it since (append-only generations keep no history of their length), and relays and the context repository as they are now.
- File names longer than 238 bytes (less on a hub whose file system allows fewer than 255: 251 on fuse-overlayfs) are not archived: the box-side worker skips them, a hub refuses them with 400 and the uploader counts them as skipped.
- Index pages read a whole directory even when the cursor skips most of it (admission-bounded).

### Configuration and tools

- `doctor apparmor-userns` warns on the development host although rootless Podman works there.
- `harness gc` treats every running devc box on the host (any state directory) as a possible user of a version; boxes started before the history file existed fall back to the version stamps.
- `devc init <git-url>` was tested with a fake git only; `devc service install` against a temporary unit directory only.
- `password_expiry_utc` is ignored by git before 2.41.

Flow steps connected only that way need `unchecked`.

### Foundations, toolbox, harnesses (X4)

1. **Confirmed (low).** **Logins never build the installer image.** `internal/harness.LoginRunner` uses the installer image without ensuring it exists or is current: a login fails if the image was removed, and after a devc upgrade it runs in the old image.

### The daemon, sessions, input, requests (X6)

1. **Confirmed (medium).** **`requestService.status` can spin.** When a box asks about its own pending request that is past its seven days and storing the expiry fails (`putLocked` error, e.g. a full disk), the loop `continue`s at once: it reloads the log, finds the request still pending and expired, and tries again, without a pause, for as long as the call lasts. The `continue` comes before both the deadline and the cancellation check, so the loop goes on past the call's deadline and after the connection closed, until storing succeeds.
2. **Fixed in C20b:** every goroutine of the daemon starts through `goTask` or `goSafe`, which end in `recoverTask`: the panic is logged with the box, the method and the frames but never its value (only a runtime error's message), only that stream or request ends, and deferred calls give back places, the box lock, login flights and worktree reads; a test fails on any other `go` statement in the package. **Confirmed (medium).** **A panic while serving a raw box stream ends the daemon.** `boxWorker.acceptStreams` starts `serveStream` with a bare `go`, not `goSafe`; `serveGit`, `serveGate`, `serveGitHub`, `serveProxy`, `serveDial` and `serveService` run there outside `proto.Conn`'s recover. The per-project goroutines of `apiProjects` (web.go) have no recover either. Everything else goes through `goSafe`.
3. **Fixed in C20a:** ingestion appends only what fits `sessions.session_journal_max`, `sessions.journal_quota` (journals counted in whole blocks plus one for the owner record) and the 1 GiB free-space reserve, notes the stop once and leaves the rest in the spool; sessions are claimed only when an event is appended; `devc sessions prune --before` makes room; `devc ps` and `devc doctor` show it. **Confirmed (high).** **Nothing bounds how much a box can make the host write to its journals.** Ingestion bounds each run (8 MiB and 20,000 events per file, 10,000 files), but not a session's journal or a project's journals over time, and there is no free-space reserve as for relay pushes. A box that writes valid events as fast as it is read (or truncates its spool file and fills it again) grows `durable/` without limit. Part 5 only says journals are never rotated.
4. **Confirmed (medium).** **Journal costs grow with the journals.** `loadJournalState` reads a whole journal for every ingestion run of its spool file (and for every host event), and reconciliation's `openSessions` reads every journal of the project twice every 30 seconds.
5. **Confirmed (low).** **A queued send can wait for months while the daemon runs.** `commander.execute` waits for rest with `waitFor(ctx, 365*24*time.Hour, …)`; only `commander.resume` at start refuses commands waiting longer than seven days, and `prune` removes final receipts only. Part 5's "a queued command older than seven days is refused" holds only across a restart.
6. **Confirmed (medium).** **`watchOnce` can run twice at once** (the watch loop and `startRefusal` of a start command). The engine is listed outside `d.mu`, so an older listing can be applied after a newer one and stop a worker that was just started, until the next pass three seconds later. Two concurrent `reload` calls (the watch loop and `fresh` in a handler) can likewise install an older configuration after a newer one until the next pass.
7. **Confirmed (medium).** **The terminal limits can be exceeded.** `termManager.open` counts the streams, then reads the window's size (a `podman exec` of up to 10 s), and inserts the stream only then; concurrent opens on a hub connection (which serves several requests at once) all pass the count. There is no reservation and no second count; opens on several local connections at once can likewise exceed the daemon's sixteen.
8. **Confirmed (medium).** **A slow box slows `devc ps` for every project.** Reconciliation holds the box's ingestion lock while it waits up to 30 s for `box.sessions`, and `sessions.list` with `sync` (and the reconcile loop) refresh the projects one after another, so a box that answers slowly delays the others by up to 30 s per call (within the two-minute budget of `sync`).
9. **Confirmed (low).** **The question hook's ordering is not guaranteed.** `boxside.askQuestion` (comment, and the `launching-a-harness` page) says the request goes out before the question is recorded, so the daemon knows the waiting hook first; the request is started in a goroutine with no synchronisation, so the question can be ingested first. `commander.answerByHook` waiting two seconds for a waiter covers this in practice. The comment and the pages now describe the code (findings G1-17, G2-16).
10. **Confirmed (low).** Smaller: `commander.lines` never forgets a session (one entry per session ever commanded while the daemon runs); `devc <harness> --prompt` without `--wait` exits 1 on `unknown`, while the input commands exit 1 only on `refused` and `typed-not-submitted`.

### Git (X7)

1. **Fixed in C20a:** a bank's fetch needs the free-space reserve and the relay within `git.relay_quota` to start, runs in its own process group under `gitx.Watch` (the push watchdog), and an ended fetch leaves no temporary pack or lock. **Confirmed (high).** **A bank has no storage budget.** `gitx.Service.fetchFromBox` fetches whatever the box's branches, snapshot refs and tags hold, with no size limit, and `gitx.Service.Bank` checks neither `git.relay_quota` nor the free-space reserve that the relay service enforces for pushes (`daemon.Daemon.serveGit`, `daemon.Daemon.watchPush`, `pushMinFree`). Banks run without the user (after every turn, every five minutes from housekeeping or the timer, before a box stops), and a snapshot takes tracked files whatever their size (`boxside.Repo.snapshotOne` limits only untracked files), so a box can fill the state file system through banks alone. Part 5's "within `git.relay_quota`" holds only for pushes through the relay service; a relay over its budget then refuses those pushes, but banks go on.
2. **Fixed in C20a:** a bank lists the box's refs first (at most 50,000, lines of at most 1,024 bytes), fetches by name only those the relay does not record, and is refused unfetched beyond 1000 changed branches, new snapshots or new tags. **Confirmed (high).** **Nothing bounds how many refs a bank fetches.** The bank's refspecs (`gitx.bankRefspecs`) copy every branch, snapshot ref and tag the box offers into `refs/devc/incoming/`; `gitx.PlanBank`'s limit of 1,000 applies only to what is recorded afterwards. A box with a very large number of refs makes every bank write them all into the relay and delete them again (`gitx.Relay.ClearIncoming`, one `update-ref` transaction), within the fetch's 30 minutes.
3. **Fixed in C20b:** the update hook writes each record with a pending marker (`refs/devc/pending/…`); a pending record counts for nothing (RefSet, `devc push`, the archive) until `gitx.Service.SettlePush` settles it: the daemon does so when receive-pack has ended and before the next one starts, a bank at its start; a record whose update git applied (branch tip or reflog, tag object) is confirmed, the others removed with their marker; box tips move only then. **Confirmed (medium).** **The update hook can leave records for updates git then refuses, and a box can use that to block a branch's records.** `gitx.Service.RecordUpdate` writes the bank ref (or tag record) before git applies the ref; git can still refuse the update afterwards, for instance when its name conflicts with an existing ref (`refs/heads/main/<t>` while `refs/heads/main` exists; git finds such a conflict when it applies the ref, after the hook; not tried). The record stays, for a tip the branch never had (harmless for history; `devc push --tag` would offer such a tag record). Because records are named `refs/devc/bank/<branch>/<unix time>`, such a refused push of `main/<t>` (from another local branch, so that no box tip is recorded with it) leaves the directory `refs/devc/bank/main/<t>/`, and a bank or push of `main` in second `<t>` then cannot create `refs/devc/bank/main/<t>`: that bank reports the work as not preserved (`devc down` refuses without `--no-bank`) and that push of `main` is refused. A box can plant such names for a range of future seconds (1,000 refs per push). Tag records (`refs/devc/tags/<tag>/<time>`) have the same weakness. Nothing is lost, every failure is closed; but `gitx.stamp` does not step past a taken name.
4. **Not a defect: the first three are clean-up opportunities, and the forward budget is deliberately computed from the updated branches, at most five of them.** Smaller: `gitx.Service.RecordPush` has no caller outside tests; `cli.ensureEmptyDir` duplicates `gitx.EnsureEmptyDir`; `devc box snapshot --worktree` is never used by the host; post-receive's forward budget (`gitx.Service.ReportPush`) is two minutes per updated branch, counting branches that `git.forward` does not name.

### Network, the SSH gate, secrets (X8)

### Data, shares, sources (X9)

1. **Fixed in C20a:** savepoints made on a box's request carry the class `requested`; their own retention keeps the newest `requested_keep` (10), named or not; the owner's retention and `before_session` never count them; at most one per `requested_interval` (10 minutes), refused with the reason; both drivers; savepoints from before count as the owner's. **Confirmed (high).** **A box can make retention drop every unnamed savepoint.** `requests.auto` defaults to `seal`, `savepoint` and `note` (`config.defaultProject`); an approved `savepoint` request runs `devc save -- <project>` (`daemon.requestCommands`), and `data.Service.Save` applies `data.Retention` after every save (`data.savepoints.keep`, default 10, unnamed savepoints only, oldest first). A box that asks for about ten unnamed savepoints (the request budget allows 20 a minute) pushes out every older unnamed savepoint, the before-session ones included: exactly those that would undo what it did to a work zone. Conversely, named requests (`devc request savepoint <name>`) are never dropped by retention and accumulate, each keeping the data as it was then (shared reflink blocks once the files change, restic snapshots in the state directory), bounded only by the request log's 16 MiB. That is no bound either: the request log is compacted past 4 MiB to its open and 200 latest closed requests (`requests.Store.compactLocked`), so approved named savepoints accumulate without limit. Part 5 does not mention either; `savepoint` may not belong in the default `requests.auto`, or requested savepoints need their own retention.
2. **Confirmed (medium).** **A trash restore that fails part-way strands the rest of the entry.** `boxside.DataWorker.trashRestore` checks every path first, then moves them back one by one with `renameat2(RENAME_NOREPLACE)` and rewrites nothing until the end, when it removes the whole entry. If a move fails after others succeeded (the box creating something at a place between the check and the move is enough; the box keeps running during the worker), the entry's `meta.json` still lists the paths already restored, and every later `devc data trash restore <id>` is refused at its check ("missing from the trash entry"). The remaining paths stay in `.devc/trash/<id>/payload/`, which only the vault can read, so getting them back needs `podman unshare` by hand. This matters most for the many-path entries of pulls and in-place restores.
3. **Confirmed (low).** **Failed reflink saves can leave copies that nothing ever drops.** `boxside.DataWorker.reflinkSave` removes `<id>.partial` when the copy, the digest or the mode record fails, but not when the final `Chown`, `Chmod` or `Rename` fails; and `data.Service.Save` writes the index record only after the worker succeeded, so a failed `appendIndex` leaves a complete `<id>` copy without a record. `savepointDrop` only ever sees IDs from the index, so such copies stay in `.devc/savepoints` (vault-owned, invisible to `devc data ls`) and hold their blocks as the data diverges. Rare, but invisible.
4. **Confirmed (low).** **The push help and the guide understate what the box can do to a staged file.** `cli.newDataPushCmd`'s help, the guide ("Moving data between machines") and part 5 say that a process holding a staged file open can change it. ### GitHub, service logins, the desktop (X10)

1. **Fixed in C20b, for `grants.secrets` and harness credentials:** `config.validateGitHubSecrets` refuses `github-token` and the realm App's `key_secret` there, in the form of the service-credential guard; `token:<secret>` is C20c's (G4-02, G4-03). **Confirmed (medium).** **A project can be granted the host's GitHub credential or the App's key as an ordinary secret.** `config.validateGrants` and `config.validateGitHub` accept `grants.secrets` naming `github-token` (`github.HostTokenSecret`) or the realm's `[github.app] key_secret`, so such a project delivers the host's credential, or the App's private key, into the box (as a file or through `host.secret`). The key is the worse case: with it a box can sign its own JWT and mint tokens for every repository of the installation with any permission the App holds, `workflows` included if the App has it, past every check of `github.Minter`. Service credentials have exactly this guard (`config.validateServiceGrants` refuses a project that also receives `value_secret`, `auth.secrets` or `_jar.<name>`); the GitHub credentials have none. A configuration mistake rather than something a box can do, but an easy one. The same holds for `grants.github = "token:<secret>"`, which `config.validateGitHub` checks only as a secret name: the token endpoint (`daemon.Daemon.githubToken`) returns whatever realm secret it names, the host's credential, the App's key or a service's credential and jar included, since `validateServiceGrants` does not look at it either (findings G4-02, G4-03).
2. **Confirmed (medium).** **A late 401 can mark a fresh cookie jar as needing a login.** `daemon.serviceManager.loginNeeded` loads the jar that is current when the upstream's 401 (or login redirect) arrives, not the jar the request was sent with, and `serviceManager.markNeeded` writes a mark with `Since = now` whenever `svclogin.State.Current` says no mark applies to that jar. If a login (automatic or `devc service login`) stored a new jar while a request with the old cookies was in flight, that request's 401 marks the new jar (whose `LoginAt` is before `Since`) as needing a login: every request then gets 503 until the next login, which with `auto` waits out the one-minute gap (`autoLoginGap`) and in the meantime answers "the automatic login did not help". `serviceManager.credential` has the same window between `loginProblem` and `markNeeded`. Concurrent requests with `auto = true` make it likely, since they all hit the 401 that starts the login.
3. **Fixed in C20b:** `cli.checkPRBranch` runs after the bank and before any push: the relay must have the branch, and it must be neither the base, the project's default branch, the relay's HEAD (the upstream's default) nor protected by `git.protected`. **Confirmed (medium).** **An approved pull request pushes before anything checks the pull request.** `cli.app.prCreate` pushes the branch (`publishBranch`, `gitx.Service.Push` with `--yes`) and only then calls `github.Client.CreatePull`; nothing compares the branch with the base. A `pr` request whose branch is the default branch (or names `--base` equal to `--branch`) fast-forwards that upstream branch and then fails to open a pull request from the branch into itself. With an empty `git.protected` (the default) the box can move the relay's `main` itself, so approving "pull request: … (main)" publishes the box's `main` to the upstream directly. The request summary shows the branch, but not that it already exists upstream or is the base.
4. **Confirmed (low).** **The first `devc gui up` builds the desktop image under the box lock.** `gui.Manager.Up` runs `gui.Manager.up` inside `box.Manager.WithRunningBox`, and `up` calls `toolbox.EnsureAuxImage` (a network build of about 470 MB on first use, and again whenever devc's desktop build files change) with the box lock held. Meanwhile relay pushes from the box (which wait two minutes for the lock, then are refused), banks and every other command on that box wait or fail. `devc gui build` beforehand avoids it, but nothing says so.
5. **Confirmed (low).** Smaller: the read facade serves the project's own repository as `upstream` says now, without the start record (`daemon.boxWorker.serveGitHub`), while tokens require the start's upstream (`box.Capabilities.GitHubToken`, finding D2-02), so changing `upstream` gives a running box reads of the new repository without a restart; `github.Minter`'s `tokens`, `verified` and `locks` maps are never pruned (one entry per distinct API, project, App, key, installation, repository and permissions for the daemon's lifetime, expired tokens included); a service stream refused for want of a relay place (`daemon.refuseBusy`, 503) or whose head never completes is not in the service log, although the service log is meant to record every request.

### The hub (X11)

1. **Confirmed (low).** **Nothing ever removes a machine, or the sessions it left live, from a hub.** `hub.Server.pruneSessions` (through `hub.machineLink.prune` or `hub.Store.PruneMachine`) removes only sessions that are not live and whose last event is older than the window; a refresh (`hub.machineLink.finishRefresh`) adds and updates sessions but never removes one the machine no longer lists; nothing deletes `machines` rows; `devc hub machines revoke` revokes the certificate only. So a machine that goes away for good (reinstalled, retired, its state directory lost) while sessions were live leaves them in the inbox for ever, marked stale, in whatever section they were (needs-you included), and their notification records stay pending. There is no command to drop a machine's projection. Part 5 says ended sessions older than 30 days are pruned, not that live ones never are.
2. **Confirmed (medium).** **Behind a proxy, a local process can pose as any registered client without its key.** In behind-proxy mode `hub.Server.identify` believes `X-Devc-Client-Cert` from any loopback peer; the certificate it carries is verified against the CA and the registry, but a certificate is not secret (machines keep theirs in `cert.pem`, `devc hub ca issue` writes `<name>.crt` 0644). Any process on the hub's server that can connect to the loopback listener and has a copy of a device's certificate can therefore send requests as that device (and, with a stolen login cookie or the password, as the user), or as a machine with a machine's certificate. The listener refuses non-loopback addresses and the documentation asks for the proxy to be the only client, but part 5 does not list this as a limit of the mode.
3. **Confirmed (medium).** **Nothing bounds how often a session is notified.** `hub.notifyKey` makes every finished turn (`finished/<done turn>/<turn>`) and every new question ID a new attention state, and `hub.notifier.update` publishes each at once (clearing the previous message), with no rate limit per session or machine. A box whose harness ends turns quickly, or that asks questions in a loop, makes the hub post to ntfy, and the user's phone ring, as often as it likes while nobody follows the session. The notifier is one goroutine for all machines and calls ntfy synchronously (up to three attempts of ten seconds each), so such a session also delays everyone else's notifications.
4. **The first part is not a defect: "use a UUID" is a valid remedy for an invalid ID and refuses no ID that is accepted; the other two are confirmed (low).** Smaller: `hub.Server.apiCommand` refuses a bad command ID with "use a UUID" although an ID of session-ID form is accepted too (`proto.ValidCommandID`); `certs`, `cert_seen` and `machines` rows are never removed, so the registry and `devc hub machines ls` grow with every certificate ever issued; a notification button's token is used up (`hub.Store.UseAction`) before the answer is forwarded, so a press whose outcome is uncertain ("Maybe not answered") cannot be repeated from the phone, only from the web app.


### Fleet and the web app (X12)

1. **Fixed in C20b:** a refusal the hub answers (507, or a 4xx; a 5xx still ends the pass) stays with its realm: a quota ends the realm's pass, another refusal only the kind it hit (files, or one repository); the realm rests ten minutes with the refusal in `devc sync status` (`error`, `quota`, `rests_until` per realm), the other realms go on; the hub-wide pause is gone. **Confirmed (medium).** **A full archive quota stops the rest of the pass, other realms included.** `fleet.Uploader.Pass` goes through the realms in name order and calls `realmPass` only while no error has occurred (`if passErr == nil`); `fleet.Uploader.realmPass` returns at the first file that fails, before the relays and the context repository; and any 507 pauses every upload to that hub for ten minutes (`quotaPause`). The realm quota (20 GiB by default) is per realm, and shared harness state is box-writable: a box that writes enough into its realm's shared harness state, or rewrites append-only transcripts so that a new generation of each is kept every hour, makes the hub refuse that realm with 507 (`hub.archiveStore.checkQuota`). From then on, until the owner prunes or raises the quota, nothing more of that realm's relays or context repository, and nothing of any realm later in name order, reaches that hub, although their own quotas have room. Part 5 says a compromised machine can fill its own part of the hub; it does not say that one box can stop the backup of other realms. Uploading the other realms (and the repositories) after a quota refusal, and pausing only the realm that is full, would contain it.
2. **Confirmed (low).** **Service logs are not archived.** `durable/realms/<realm>/service-log/<name>.jsonl` (`paths.Paths.ServiceLogFile`, one line per request a box made to a service: time, box, method, path, status) is not among the kinds `archive.ValidRel` accepts and `fleet.hostFiles` does not list it, so it is neither uploaded, exported nor restored, while the network and gate logs are. The archive's package comment listed the durable state as it was before services existed (C18); session-owner records (`durable/session-owners/`) are not archived either. Possibly deliberate for the owner records; for the service log it looks like an omission.
3. **Confirmed (low).** **A ref log that outgrows 64 MiB can no longer be resynchronised or restored.** A repository's `refs.jsonl` on the hub gets a line for each upload pass in which the repository's refs changed (banks, snapshots and pushes add refs) and is never compacted. `fleet.Uploader.resyncRepo` reads it whole with a cap of `maxRefLog` (64 MiB) whenever the bookkeeping is not in sync (lost or rebuilt `state.json`, a 409 on a bundle or ref log, a cut line), and fails beyond it, which (item 1) also ends the pass for everything after that repository; `fleet.Restorer.Restore` refuses a ref log above 64 MiB and stops the whole restore. At a few hundred bytes per change this takes years of busy use, but nothing warns as it approaches.
4. **Confirmed (medium).** **`devc secret pull` shows the hub's labels and takes any machine's newest bundle.** The machine, version and time it prints (`cli.newSecretFleetCmds`) come from the hub's JSON (`archive.SecretsReply`), not from the sealed `fleet.SecretSet`, whose `Machine` and `Created` are authenticated but never compared or shown. Without `--machine`, `hub.Server.apiSecretsGet` returns the newest bundle of the realm from any machine, and any enrolled machine may push one under any realm name: one that does not know the passphrase makes every later pull fail ("the passphrase is wrong or the data is damaged"); one that knows it (a machine that once pushed) decides what pulls add, or replace with `--overwrite`. A hub can likewise serve an older version. Pull could compare the sealed machine and time with the reply and print them.
5. **Confirmed (low).** **`devc hub archive prune` says it is "the only way anything leaves the archive."** Its `Long` help in `cli.newHubArchiveCmd` says so, but the server removes mutable generations by retention (`hub.archiveStore.retain`) and secrets bundles beyond the newest ten. `hub.PruneArchive`'s doc comment said the same and has been corrected; the help text is code and was left.
6. **Fixed in C20b:** only a receipt settles a prompt: `settleOutbox` only notes a prompt event whose whole text (or, truncated, a prefix) is a waiting prompt's, and `setOutbox` takes a prompt out eight seconds after its final receipt, delivered or not. **Confirmed (medium).** **A box can settle a prompt the web app is still waiting for.** `settleOutbox` in `web/app/store.js` takes a `prompt` event as the arrival of a waiting prompt when the waiting text begins with the event's text (its first 200 characters), and then deletes that command's pending entry, so its receipt is never asked for again. Prompt events come from the box's hooks; an event with a short text such as `y`, or a prompt typed by someone else that begins the same way, makes the app show an undelivered or uncertain prompt as arrived. Since the comparison trims the event's text first, an event whose text is only spaces (a valid prompt event) settles the first waiting prompt whatever it says (finding G5-23). Matching the event's full text, or keeping the pending entry until a receipt arrives, would avoid it.
7. **The first part is not a defect: the two functions have no effect; the others are confirmed (low), the expired receipt (medium).** Smaller: `fleet.hashRange` and `fleet.sha256Hex` have no callers. `clearCache` in `web/app/store.js` is never called and the app has no way to log out (the hub's `POST /api/logout` is unused), so the session summaries in local storage (with last messages and questions) stay on the device after a login ends or a certificate is revoked. `resolvePending` marks a never-confirmed command "did not arrive" on any 404, and the daemon prunes receipts after seven days (`daemon.receiptKeep`): a command whose answer was lost, saved in local storage on a device that comes back more than a week later, is offered for **Send again**, which the daemon would then apply as new. `fleet.ExistingState` does not count `service-log/` or `gate-log.jsonl.1` as existing state.

### Found by the accuracy review

The accuracy review (`docs/dev/reviews/G1-review.md` to `G5-review.md`) checked the explorer's pages against the code. Where a page described a rule and the code turned out to do something weaker, the page now describes the code and the gap is listed here. Nothing was changed in the code.

1. **Fixed in C20b:** only the start that ran the container writes the capability record; `up`, `sh`, `run`, `root`, `devc <harness>` and the daemon's session start refuse a running box without its readiness marker or a record of its container ID (`box.CheckStarted`) and ask for a restart. **A box can receive grants added after its start without a restart (finding G1-01).** `box.Manager.up` finishes the start of a running box that has no readiness marker without restarting it, and `box.Manager.afterStart` then writes a new capability record from the current configuration (`box.Manager.recordCapabilities`). The marker is box-writable (`/run/devc/ready`), so a box that deletes it gets its record rewritten at the next `devc up`, `sh`, `run`, `root`, `worktree`, `forward`, `editor`, `gui up` or session start from the host (all of them go through `box.Manager.ensureRunning` or `up`), once it writes the marker again. Secrets for `host.secret`, SSH hosts, allowlist entries, GitHub grants and services added to the configuration while the box ran then reach it, although the rule (`internal/box/capabilities.go`, finding C1-02) is that adding a grant needs the box to be brought up again. The definition hash must still match, so a drifted box is still refused, and at level internet the binding and the rules are verified first. Intersecting the new record with the previous one on this path would keep the rule.
2. **`session.ParseLive` ignores whatever follows the first JSON value (finding G2-05).** Its comment said that anything unexpected rejects the whole report. On the engine path (`session.QueryLive`: every reconciliation of the CLI, as in `devc ps`, `attach` and the stop hooks, and the daemon's while the box's channel is not connected) `[] garbage` counts as an empty report, so every open session of the box ends as `lost`. A box can print `[]` alone to the same effect, so this gives a hostile box nothing new; it matters for output broken by accident. The daemon's path over the channel decodes strictly.
3. **A seal request outside the data root tells the box the host's path of its data root (finding G2-01).** `daemon.requestService.create` returns `data.Normalize`'s error through `invalidParams` as a JSON-RPC error, which `proto.Conn.serve` passes to the box unchanged, and the message names `data.Project.HostRoot` (the projects root, typically below the user's home). `proto.Conn.serve`'s comment said that nothing of the host's internals reaches the peer. A path, no content.
4. **The daemon addresses a box by its name after checking its labels once (finding G2-06).** `daemon.Daemon.watchOnce` checks the realm and project labels when it lists the containers (every three seconds); `commander.runStart`, `commander.stop` and the terminal's exec (`termManager.open`) later run `podman exec` on `devc-<realm>-<project>` by name, checking neither the labels nor the container ID again. A container put under that name in between would receive the exec. Only the host's user (or devc) can create one, so a box cannot use this; the channel checks the container ID at every connection.
5. **`devc wt rm` removes what snapshots leave out (findings G3-01, G3-19).** Its help says nothing is removed unless the worktree's uncommitted work was banked, and `cli.newWorktreeCmd` banks first in a project with a relay ("--force does not change that", finding B4). But a snapshot (`boxside.Repo.snapshotOne`) takes no ignored file and leaves out untracked files over 10 MiB, nested repositories and special files, and `gitx.Preserved` counts only what the snapshot took. `boxside.Repo.Dirty` asks `git status`, which does not count ignored files, so ignored files (build outputs, `.env`, data a `.gitignore` names) go with every removal, `--force` or not (tried with git 2.43: `git worktree remove` deletes them); the left-out untracked files go with `--force`. Without a relay nothing is banked and `--force` removes a dirty worktree outright. Refusing a worktree with ignored or left-out files unless `--force` (and saying so) would match the help.
6. **A seal of a regular file can be recorded for a file that was not sealed (finding G4-01).** `boxside.DataWorker.seal` takes a regular file's identity from its first `Lstat`, then `ownFile` opens the name again and re-owns whatever it finds; the final check compares the name with the first `Lstat`. A box that renames another file over the name before the open and puts the original back before the check (it keeps running during the worker) gets a seal record and a digest (computed after the check, of the original) for a file it can still write, while the other file is sealed wherever it went. The comment says the check catches a rename; it does for directories, whose identity comes from the opened descriptor. Comparing with `ownFile`'s `Fstat` would close it.
7. **Sessions the daemon starts take no before-session savepoint (finding G4-17).** `data.savepoints.before_session` is honoured by `cli.app.saveBeforeSession`, which only `devc <harness>` (`cli.app.prepareSession`) calls. `daemon.commander.runStart`, used for sessions started from the web app and the hub (`session.start` commands), runs `devc box session start` in the box directly, so those sessions start without a savepoint and without the refusal when one fails. Work order C06 named only `devc <harness>`; the daemon's starts came later (C09, C12) without it.
8. **The web app can stop following the hub until the page is reloaded (found while checking finding G5-19).** When the stream's `EventSource` closes for good (the hub, or a reverse proxy in front of it, answered with an error instead of the stream, as a proxy does with 502 while the hub restarts), `web/app/stream.js` asks `/api/me` (`checkAuth`) and schedules a reconnect only if that succeeds. If the hub cannot be reached at that moment, `checkAuth` sets `auth` to `offline` and nothing schedules another try: `onVisibility` reconnects only while `auth` is `ok`, and `begin` in `main.js` retries only until the first start. The app then shows "Offline" with its saved data until the browser fires `online` (a change of the device's network, not the hub's return) or the page is reloaded; after a reconnect through `online`, `auth` stays `offline`, so the app says "Offline" while the stream is live. Ordinary network errors are not affected: the browser keeps such a source and reconnects by itself. Scheduling a retry when `checkAuth` reports `offline`, as `reconnect` does after a failed snapshot, would close it.
9. Smaller: a harness that exits before `tmux.TagWindow` has tagged its window gets no `session.end` from the pane-died hook (the hook finds no session option), so its session ends as `lost` at the next reconciliation rather than with its exit status (finding G1-14). After a failed ingestion run the ingester skips its 50 ms pause, so hints keep starting failing runs without it; the frame inspector's stream budget still bounds the hints (finding G2-11). `commander.resume` refuses an unfinished command accepted more than seven days ago before it looks at `delivering`, so a command that may already have typed is reported `refused` (expired) rather than `unknown` (finding G2-24). A host event follows only what one bounded ingestion pass took in, and also when that pass failed (`daemon.Daemon.recordHost`), so older box events can come after it in the journal (finding G2-09). The CLI's journal reader takes a last event that lacks its newline, the daemon's follower does not, so after such a crash `devc ps` can differ with and without the daemon until the next append (finding G2-19). `session.Store.Claim` runs before a spool file is read, so an empty or wholly invalid file claims an unowned session ID (finding G2-17). `devc login` and `devc secret set` say "'devc up' delivers it", but `up` of a running, ready box delivers nothing (finding G1-08). A push accepted by `pre-receive` can leave the relay over `git.relay_quota` by what the update hooks then write (records and their reflog entries); the next push is refused (finding G3-07). An SSH gate session goes on after its grant was removed: the daemon and gate-exec check only when a session starts, and only closing the master (`devc ssh close`) ends running ones (finding G3-02; the spec promises only that). With `data.savepoints.driver = "none"`, `before_session = true` silently takes nothing (`data.Service.BeforeSession`). An in-place restore that fails in its second pass (a full disk, a change by the running box) keeps what it already replaced; the displaced entries are in its trash entry (finding G4-12). `devc data pull` and `push` ask nothing when the preview counts no regular file, although directories and symlinks then arrive (`cli.app.runSync`, finding G4-09). A service request without a declared length streams its first `max_body` bytes to the upstream, with the credential, before it fails (`svclogin.Proxy.ServeHTTP`, finding G4-15). `gui up` checks the desktop's limits only after `box.Manager.WithRunningBox` has started the box (finding G4-18). `data.DecodeResult`, `gitx.decodeStrict` and the other decoders that end with `json.Decoder.More` accept a stray `]` or `}` after the value (finding G4-24); what they decoded is unaffected. Credential files are kept out of the archive by the machine alone: the hub accepts any harness path (`archive.ValidRel`), so a hostile machine can store one, and credential content a box copies to another name in the shared harness state is archived by an honest machine too (finding G5-02). The hub sends `terminal.close` only after `terminal.open` answered validly (`hub.Server.apiTerminal`): a stream the daemon opened whose answer came after the hub's 30 seconds, or was rejected, stays open on the machine, holding one of the connection's four places, until its session ends, the link closes, the client exits or twelve hours pass (finding G5-06). `loadSnapshot` in `web/app/store.js` replaces every session summary and keeps the higher of the old and the snapshot's position, so a snapshot that began before a detail read finished brings back the older summary, and stream changes of that session below the detail's position are then refused as older; the reload of open sessions that follows a snapshot repairs the open ones (finding G5-07). A re-read (`hub.machineLink.finishResync`) takes the machine's view and applies every returned event above the view's seq without checking that the seqs follow one another, so a compromised machine can make the hub's tail of its own session skip numbers (finding G5-08). A notification record still pending when its state ends is dropped without a clear (`hub.notifier.update`), so a publish that reached ntfy although its answer was lost leaves its message on the phone (finding G5-17). Stream positions are bare numbers: `hub.Server.apiStream` resets only a position beyond its newest change or below what its change log holds, so a position from another hub's numbering (a new database at the same address) that falls within the range is resumed from as if it were this hub's (finding G5-18). `devc secret push` counts the passphrase's bytes (`cli.app.readPassphrase`) while its message says characters, so three four-byte characters pass the minimum of ten (finding G5-26); the confirmation, a refused passphrase, the values a push reads and the values a pull did not reach after a store error are never cleared (finding G5-27).

### Found while fixing them (C20b)

1. **Goroutines outside the daemon package still end the daemon on a panic.** `goTask` covers every `go` statement in `internal/daemon`, but packages the daemon calls start their own: `netpolicy.Proxy` copies a box's bytes to the upstream (`proxy.go`, the CONNECT pump) and rechecks a connection's policy in goroutines of its own, `gitx` pumps a bank's input (`box.go`), and `net/http`'s transport runs the router's `DialContext` (`daemon.router.dial`, `netpolicy.Forwarder.Dial`) in its own goroutines. None of them recovers. Their bodies are small (copies, a timer loop), but a panic there is not contained.
2. **An interactive vendor login is escaped as a whole stream.** With X4 2 fixed, a login's colours, cursor movements and the echo of a backspace show as `�`; the built-in logins (a URL, a device code, a pasted code) stay usable, a menu drawn with cursor movement would not. Passing a safe subset of escape sequences (colours, cursor movement) would need a terminal filter of its own; not done.
3. **A box without its readiness marker is not reconciled.** `session.Store.refresh` returns early for a running box that is not ready (`st.Running && !st.Ready`), so the CLI and the daemon never end such a box's sessions as lost while it runs; since C20b nothing finishes its start either, so this lasts until it is restarted. The box can do this to its own sessions only.
