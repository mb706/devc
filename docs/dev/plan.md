# Implementation plan for devc v2

The product spec is `specs-v2.md`. This file records how it is built: the process, the package map, the technical decisions that cut across chunks, and the chunk list. Work orders in `docs/dev/chunks/` add the detail for each chunk.

## 1. Process

- An orchestrator writes one work order at a time and hands it to one implementing agent. Chunks run strictly in sequence; each starts from the committed result of the previous one.
- The implementing agent does not commit. The orchestrator commits to `master` after reading the agent's report.
- Reviews by a second model happen at four points only: after C03, and at the end of phases 1, 2 and 4 (phase 3 is reviewed together with phase 4). Each review is followed by one fix chunk.
- Nothing is verified against real harness accounts. Everything that would need one is listed in `LEFTOVER.md`.
- VM-backed realms are out of scope until a machine with KVM is available.

## 3. Cross-cutting decisions

### 3.1 Identity and names

- Box container name: `devc-<realm>-<project>`. Box ID (for short runtime paths): first 12 hex characters of SHA-256 of `<realm>/<project>`.
- In-box user `dev`, UID and GID 1000, home `/home/dev`. Vault UID and GID 2000.
- In-box paths: project `/w/<realm>/<project>`, context `/ctx/notes` and `/ctx/memory`, toolbox `/opt/devc`, runtime `/run/devc`, generated files `/etc/devc`.
- Session ID: `s` followed by 20 lower-case base32 characters, time-ordered. Generated by devc only.
- Labels on every Podman object devc creates: `devc.realm`, `devc.project`, `devc.role` (`box`, `gateway`, `helper`, `aux`), `devc.confighash` on boxes.

### 3.2 Paths

`internal/paths` is the only place that knows the layout of spec section 5. Overrides for tests and unusual setups: `DEVC_CONFIG_DIR`, `DEVC_STATE_DIR`, `DEVC_RUNTIME_DIR`, and `projects_root` in `config.toml`. Runtime directory per box: `<runtime>/<box-id>/` with `spool/` and, from phase 2, sockets.

### 3.3 The in-box helper

The same static binary, mounted from the toolbox at `/opt/devc/bin/devc`. Its in-box subcommands live under the hidden command group `devc box …` and in package `boxside`:

| Subcommand | Purpose | Chunk |
|---|---|---|
| `box init` | container command: prepare home, link dotfiles, then wait | C02 |
| `box launch <harness>` | what a shim runs: fetch credential, set env, register session, exec the real binary | C03 |
| `box hook <kind> <event>` | harness hook receiver: read JSON on stdin, write a normalised event to the spool | C04 |
| `box session …` | create a tmux window for a session, attach | C04 |
| `box snapshot` | create a snapshot commit of a worktree | C05 |
| `box dial <addr>` | connect stdin/stdout to a TCP address; used by the forwarder after `nsenter` | C07 |
| `box seal-worker`, `box copy-worker` | run in the helper container: chown/chmod, reflink copy, move from staging | C06 |
| `box pty` | status wrapper answering OSC 7501 | C10 |
| `git-remote-devc` (argv[0]) | git remote helper for the `devc::` scheme | C05 stub, C11 real |

The helper container is `podman run --rm --network none --rootfs <toolbox>/helper-rootfs:O …` with only the target tree mounted and only the capabilities the worker needs.

### 3.4 Podman usage

- All calls go through `internal/engine`, which shells out to the configured engine binary and parses JSON output. No Podman Go bindings.
- Box creation flags are in spec section 6.2. The network-related part differs by level (3.9).
- SELinux hosts (detected through `/sys/fs/selinux/enforce`): add `label=level:<realm level>` when the realm sets one; never use `:z` or `:Z`; run `restorecon -R` on the project directory during `devc up` when the tool exists. `devc doctor` checks the file-context rule and prints the `semanage` commands.
- `devc root` is `podman exec --user 0 --privileged`.
- Drift: `devc.confighash` is a hash of the rendered create arguments plus image ID. `devc up` compares and offers `--recreate`.

### 3.5 tmux model

- One tmux server per box, started by the first session, using the toolbox's static tmux and a devc-owned config file (`-f /etc/devc/tmux.conf`) that includes the user's dotfile if present.
- One tmux session named `devc`; one window per devc session, named `<worktree>/<harness>` and tagged with the user option `@devc_session=<id>`.
- Every attaching client gets its own grouped session (`new-session -t devc`, `destroy-unattached on`), so clients can look at different windows.
- Attach from the host: `podman exec -it --detach-keys= -e TERM -e COLORTERM <box> … tmux attach`.
- tmux settings required by the harness TUIs: `allow-passthrough on`, `focus-events on`, `extended-keys on`, `mouse on`, generous `history-limit`.

### 3.6 Events and journal

- An event is one JSON object per line: `{"v":1,"seq":N,"ts":"RFC3339Nano","session":"s…","type":"…","data":{…}}`.
- Types: `session.start` (harness, worktree, cwd, pid), `session.end` (reason), `state` (`idle|working|blocked|done|error`, optional `kind`), `prompt` (text hash, length, optional text), `question` (id, text, options), `message` (final assistant text, truncated), `tool` (name, one-line summary), `note` (free text from devc itself).
- In the box, events are appended to `/run/devc/spool/<session>.jsonl` without `seq`. The host ingests spool files through `safefs`, validates them, assigns `seq`, and appends to `<state>/durable/realms/<realm>/journal/<project>/<session>.jsonl`. Ingestion tracks byte offsets per spool file in `local/`.
- Phase 1 ingests on demand (`devc ls`, `devc bank`, the timer). The daemon tails continuously from phase 2 and also receives events over the box channel.

### 3.7 Git

Model: the box sees the relay as `origin`. Refs in the relay are in spec section 9.2.

- Host git commands run only against the relay (a bare repository whose config and hooks are host-controlled). Box-side git always runs via `podman exec` as `dev`.
- Transport between relay and box in phase 1 is host-initiated: `git fetch`/`git push` on the host with the remote `ext::<engine> exec -i <box> %S /w/<realm>/<project>/.repo` and `-c protocol.ext.allow=always` for that invocation only. `%S` expands to `git-upload-pack` or `git-receive-pack`, which run inside the box.
- `bank`: fetch `+refs/heads/*:refs/devc/incoming/*`, then for each incoming ref apply the policy (spec 9.2), update `refs/heads/<b>`, and record `refs/devc/bank/<b>/<unix-time>`. Snapshot commits come from `box snapshot` in each worktree and land in `refs/devc/snap/<worktree>/<unix-time>`. Relay config: `gc.auto=0`, reflogs for all refs, `fetch.fsckObjects=true`, `receive.fsckObjects=true`.
- `pull`: fetch GitHub into `refs/remotes/github/*` with the host's own credentials; fast-forward relay heads where possible; then push `refs/heads/*` to the box as `refs/remotes/origin/*` and `refs/remotes/github/*` as the same.
- `push`: relay to GitHub, explicit branch, `--force-with-lease` only with `--force`.
- In the box, `remote.origin.url` is `devc::<realm>/<project>`. In phase 1 the remote helper is a stub: fetch succeeds as a no-op with a one-line explanation, push succeeds as a no-op saying that commits are banked by devc and reach GitHub through `devc push`. From C11 it is a real transport through the daemon.
- Box repository layout: `git init --separate-git-dir /w/<r>/<p>/.repo /w/<r>/<p>/main`; task worktrees are siblings created with `git worktree add`. Box git config: `gc.auto=0`, `maintenance.auto=false`, identity from the realm.

### 3.8 Data

- The data root (default `data/`) is a sibling of `main/` in the project directory. Each worktree gets a `data` symlink pointing at it if the project defines data.
- Project directory and zone directories that hold sealed children are owned by the vault UID with mode 1777. Setting this up, sealing, unsealing, trash moves, reflink copies and moves from staging all run in the helper container (3.3).
- Savepoints: `reflink` driver copies the work zones into `.devc/savepoints/<id>/` with `FICLONE`; `restic` driver runs a pinned static restic from the toolbox in the helper container against a repository in `local/savepoints/`; `borg` is optional and runs in an auxiliary image. `auto` picks `reflink` when a probe clone succeeds, else `restic`. Each savepoint has a small metadata file: id, time, name, git commit of `main`, driver, paths.
- Sync (C16): rsync on the host over the user's own SSH, into a staging directory under `local/`, then moved into the data root by the helper container. Defaults: no `--delete`, `--backup-dir`, `--partial`, dry-run preview unless `--yes`.

### 3.9 Network

- Phase 1 (C07): level `open` is the engine default; `none` is `--network none`; `internet` is the engine default network plus rules installed by the host. Sequence: `podman create`, `podman init`, read the network namespace path and the box's resolver addresses, `podman unshare nsenter --net=<ns> nft -f -` with a default-accept output chain that drops private, link-local, CGNAT, multicast and loopback-range destinations except the resolver on port 53, then `podman start`. IPv6 is disabled by sysctl. After start, a canary inside the box must fail to reach the host's LAN address; otherwise `devc up` stops the box and fails.
- Phase 3 (C15): per-realm internal network, gateway container with forwarding, NAT and the same drop rules, default route installed from the host. `allowlist` adds a CONNECT proxy (part of the devc binary) with domain rules, and the box has no resolver. Exceptions are nft set elements with timeouts.
- Forwarding (C07): the host listens on loopback; for each connection it runs `nsenter -t <pid> -U -n --preserve-credentials <devc> box dial 127.0.0.1:<port>` and relays.

### 3.10 Secrets and logins

- Secret store interface with a file backend first (`durable/realms/<realm>/secrets/<name>`, 0600, directory 0700).
- `devc login <realm> <harness>` runs the manifest's login command interactively in a throwaway container. For `env-token` harnesses it then asks the user to paste the token (hidden input) and stores it. Nothing parses vendor output.
- Delivery in phase 1: at `devc up` the granted secrets and tokens are written to a tmpfs directory mounted only into that box (`/run/devc-secrets`, 0400). From C11 the launcher asks the daemon instead and nothing is stored in the box.

### 3.11 Daemon and hub (phase 2)

- Protocol: JSON-RPC 2.0, one object per line, the same on the daemon's Unix socket, on the box channel streams and inside WebSocket frames to the hub.
- Box channel: the in-box helper listens on `/run/devc/helper.sock`; the daemon connects from the host and runs yamux over it. In-box clients talk to the helper through a second, box-local socket; the helper relays. Requests from a box are attributed by which channel they arrive on.
- Streams: `subscribe {epoch, seq}` returns a snapshot or a replay; events carry `seq`; a heartbeat every 15 s; `missed` forces a new snapshot.
- Commands carry a client-issued ID. The daemon stores a receipt per ID before acting and returns the stored receipt on a repeat.
- Hub: SQLite (pure Go) for projections and a bounded event log. Two listeners: machines and users. TLS client certificates are checked by the reverse proxy or by the hub itself; `devc hub ca` creates the CA and issues certificates. Users additionally pair a device and register a passkey.
- Several hubs: the daemon connects to every hub listed; only the first connected one is asked to notify.
- Web app: static files embedded in the binary, no bundler. Vendored Preact with htm and xterm.js.
- Requests have a risk class. Low-risk requests (seal, savepoint, restart a session) may be approved through the hub. High-risk ones (network exceptions, new grants, root commands, pushes to GitHub) can be approved only on a machine with the CLI until a non-theatrical remote approval exists (section 5).

### 3.12 Gate (C11)

`sshd -i` per connection, started by the daemon with a generated config: one host key per machine, `AuthorizedKeysFile` per box with `restrict,pty`, `ForceCommand devc gate-exec <host>`, all forwarding disabled, no subsystems except sftp mapped through the forced command. The forced command runs `ssh -S <master> -o ControlMaster=no <host> -- "$SSH_ORIGINAL_COMMAND"` with a TTY when one was requested. In the box, `~/.ssh/config` entries for granted hosts use a `ProxyCommand` that opens a channel stream to the gate.

### 3.13 Testing

- A fake harness (`test/fakeharness`) behaves like an interactive agent enough to test sessions: it prints a prompt, reads lines, calls the hook receiver, optionally emits OSC 7501, and can be told to edit files or run git.
- The escape suite (end of phase 1, extended later) runs inside a box and must fail to: modify or delete sealed data, write the relay or any `refs/devc/*`, read another realm's state, reach a LAN address, change its own mounts or network rules, write policy files, or gain UID 0.

## 5. Device-signed commands: decision

Not built. A signing key held by the web app does not protect against a compromised hub, because the hub serves the web app's code and can make the browser sign anything while the app is open. The hub is also trusted for transcripts and notifications regardless.

What is done instead:

- The hub sits behind client certificates, and the daemon accepts only box-scoped commands from it.
- Requests carry a risk class; high-risk approvals are not accepted through the hub (3.11).

A design that would give real benefit, recorded for a later decision: for high-risk approvals only, require a WebAuthn assertion whose challenge is the hash of the request, verified by the machine daemon against device keys enrolled out of band. A compromised hub could then not approve anything silently; at worst it could misuse one approval gesture while the user is approving something else. It costs an enrolment flow and a tap per approval.
